# Award Day実機受入試験

2026-11-15の実演、11-12のデモ版固定に向けた実施用手順。既存の[検証状況](../../verification.md)と[実機ゲート](../architecture/validation-gates.md)を補完する。過去の観測やIssueの開閉は、そのまま最新版の合格を意味しない。

## 実施の境界と順序

1. 対象コミット・exeのSHA-256・操作定義・Minecraft設定を固定し、既存自動試験を実行する。
2. Android 1台＋dry-runで表示・実通信・入力ライフサイクルを調べる。
3. 人がPCに常駐し、疑似ゲーム画面で実Windows入力と停止を確認する。
4. Android・iPhoneを含む3台で無線接続・管理権・障害復旧を確認する。
5. Minecraftの短いデモを反復し、本番配布物で別PCでも確認する。
6. 第三者の試遊を記録し、11-12までに本番版と予備手段を固定する。11-13〜14は同じ版の通し稽古と会場条件の確認、11-15は始業確認を行う。

無人で許されるのはdry-run・シミュレーションとテスト画面内のAndroid操作だけ。ロック解除・認証・USB許可・実Windows入力・実ゲーム・永続設定変更は人が行う。安全停止が失敗したらその系列を中断し、実入力を再開しない。

判定は「合格」「不合格」「未実施」「保留」。期待値・準備済み・CI成功を観測結果へ書き換えない。部分合格は条件ごとに行を分ける。

## 現行仕様の読み替え

- [可変人数](../decisions/2026-10-25-variable-players.md)：現行はP1を含む2〜4人。5台目が満員。#38等の旧本文にある「必要人数3」「4台目拒否」は現在の合否条件に使わない。本番は3人で固定する。
- [二段階Ready](../decisions/2026-10-25-two-stage-ready.md)：接続と協力開始は別。PCの分担決定→P1のPREPARE→明示READY。再開にも参加者・対象・停止手段が必要。
- [画面統一](../decisions/2026-10-26-unify-controls.md)：3人Minecraftも生成画面と`act:<ID>`を使う。役割・入力先・epoch・通信契約は[通信仕様](../../protocol-specification.md)を参照する。
- 自動復帰は実装初期値と採用判断を分ける。ON/OFF、期限内/外、ホストPAUSEを別々に試す。本番で許す条件は未決定のまま記録し、試験だけで採用を決めない。

## Android USB dry-runの再実行

既存Node 22以上・認可済みADB・Chrome・確認したソースからビルドしたRust exeを用いる。新しいアプリや依存パッケージは不要。

```powershell
# リポジトリのルートで実行。ADBがPATH外なら実際の導入先を指定する。
$adbPath = "$env:LOCALAPPDATA/Android/Sdk/platform-tools/adb.exe"
& $adbPath devices
# device が1台、画面が解除済みでなければ操作せず保留する。
# SETUP_WINDOWS.mdに従って同じソースをビルドし、実行前にinput.rsのdry-run分岐を確認する。
$hostPath = (Resolve-Path apps/host-rs/target/release/recooplay-host.exe).Path
$hostHash = (Get-FileHash -LiteralPath $hostPath -Algorithm SHA256).Hash
node scripts/device/android-dry-run.mjs --adb $adbPath --bin $hostPath --sha256 $hostHash
```

[補助スクリプト](../../../scripts/device/android-dry-run.mjs)はハッシュを照合して、子プロセスの`RECOOPLAY_DRY_RUN=1`・`RECOOPLAY_NO_CONFIG=1`・疑似入力先を強制する。起動後も疑似対象と初期の内部押下ゼロを確認する。`inject.mode=on`は論理モードであり、dry-runの無注入とは別の値。API表示だけを無注入の証拠にしない。exeの由来確認を省略しない。

端末1台とロック状態を確認し、ホストがPCのループバックに割り当てた空きポートをADB reverseで転送する。ADB forward側も空きポートを自動割当する。Chromeデバッグを利用できない場合は操作試験を保留し、端末に残った試験タブを手動で閉じる。端末なしで起動・HTTP・監視接続・正常終了を確認するには、上記コマンドから `--adb $adbPath` を外して `--host-only` を付ける。

これは**USB TCPの試験**。WebSocketの実通信とAndroid上の描画は確認できるが、Wi-Fi、UDP WebRTC、LANでのPC専用エンドポイント拒否、ゲーム応答の証拠ではない。ADB reverseはPCからループバックとして見えるため、スマホで`/app`・`/host`・管理APIを開かない。補助の2参加者はPC上の模擬WSであり、3実端末に数えない。

結果・画像・ホストログはGit対象外の`data/local/device-acceptance/`へ保存する。raw画像・ログには個人情報が混在する可能性があり、そのまま公開しない。公開は必要な値だけを選んだ記録にする。スクリプトは自分が作成した転送・テストタブ・ホストだけを片付ける。ADBサーバーや既存Chrome全体を停止しない。異常終了時は、自分の実行記録のポートだけ`adb reverse --remove tcp:<port>` / `adb forward --remove tcp:<port>`で除去する。

## 受入ケース

全ケース共通：次節の記録票を複製し、期待結果と実測を分ける。端末にはA/B/Cの別名を付ける。実Windows入力以降は人が停止操作できる状態を必須とする。

Wi-Fiでdry-runを行う場合は、信頼できる同一LANにPCと端末を接続し、試験用PowerShellから起動する。USB用スクリプトと分けて、LANから到達できる既存のホスト起動経路を使う。

```powershell
# 同じコミットからビルドしたexeと画面資産を使用する。
$env:RECOOPLAY_ROOT = (Get-Location).Path
$env:RECOOPLAY_DRY_RUN = '1'
$env:RECOOPLAY_NO_CONFIG = '1'
$env:RECOOPLAY_FAKE_TARGET = '1'
$env:RECOOPLAY_STDIN_CONTROL = '1'
Remove-Item Env:RECOOPLAY_RUNTIME_MEASURE -ErrorAction SilentlyContinue
& $hostPath
```

PCの `/app` に表示されるQRで参加し、PCの `/host` で状態と入力を観測する。入力先の疑似喪失はホストの標準入力に `target off`、復帰は `target on`、停止は `stop`、終了は `quit` を入力する。ホットキーと実際の前面切替はAT-D04で別に確認する。終了後は試験用PowerShellを閉じる。監督下の実入力試験は、別の起動で[構築手順の実入力と緊急停止の案内](../handoff/SETUP_WINDOWS.md)に従う。

### AT-D01：端末表示・Pointer（#10）

- 前提：Android Chrome・iPhone Safariそれぞれの版を記録。最初はdry-run、入力の流れをモニターで確認する。
- 操作：P1/P2/P3の各担当で生成画面を開く。ボタンのタップ・長押し・領域外へドラッグ、スティックの8方向・中央復帰、視点の短い/長いドラッグ、リモコンのタッチパッド・クリック・2指スクロールを行う。
- 複数指：同じボタンを2指で保持→片指を離す→最後を離す。別ボタンとの同時操作、スティック＋ジャンプ、視点＋別ボタンも行う。ADB単指や合成Pointerの試験は実指2本の代替にしない。
- 停止操作：保持したまま回転、HOMEで非表示、画面ロック、診断を開く、Pointer cancel/capture喪失が発生する操作を各1系列ずつ行う。実イベントを取得できなければcancel発生済みとは書かない。
- 期待・合格：画面外にはみ出さず操作できる。最初の指だけdown、最後だけup。停止時は全解放・未処理視点破棄、復帰だけでは旧押下が戻らず新しい押下が必要。各系列3回で残留ゼロ。端末別に画面・入力時系列・イベントの種類を保存する。

### AT-D02：3台・役割・管理権（#38）

- 前提：A=Android/P1、B=iPhone/P2、C=追加スマホ/P3、同一ローカルネットワーク。役割はサーバーの割当を記録する。
- 操作：1台でReady不可→2台で現行条件を確認→本番3台で分担決定・PREPARE・READY。30秒間、移動・視点・採掘を同時操作。P2/P3からの管理命令・担当外入力を既存通信試験と実画面で確認する。Pause中に担当交換→変更本人の確認前は再開拒否→確認後に再開。再接続後の元の枠・P1管理権も確認する。
- 期待・合格：担当通りに反応し、P1管理権を維持。交換とepoch変更で旧押下・旧視点は戻らない。3系列成功、混線・無断管理操作・残留ゼロ。各端末表示・割当・command_result・入力ログを対応付ける。4台/5台境界は別端末があれば追加し、なければシミュレーションのみとする。

### AT-D03：通信断・復帰（#39）

- 前提：まずdry-run、実入力はAT-D04合格後に人の監督下で実施。復帰設定・15秒窓・実経路を記録する。ネットワークの永続設定は試験者が確認して扱う。
- 操作：全員がキー/マウス保持＋視点移動中に、A/B/Cそれぞれのタブ閉鎖・非表示・スリープ・Wi-Fi切断を一つずつ試す。ONで期限内/外、OFF、P1不在、RTC未成立、対象外、緊急停止後、明示PAUSEを別系列にする。期限の起点はホストの切断検知時刻も保存する。WSだけの遮断、RTCだけの不成立と両方の断を区別する。
- 期待・合格：検知時に全員の合成入力を解放し、連打待ち・視点待ちを破棄。復帰後も同じ枠と管理権。OFF・期限外・明示PAUSEは明示RESUMEまで停止。ON期限内も安全条件が揃わなければ再開しない。旧epoch再送・旧RTC世代からの入力は反映しない。各系列3回で残留ゼロ。ブラウザ・ホストの検知時刻/停止時刻・epoch・押下集合・復帰画面を保存する。4秒は監視の設定値で、物理停止時間の保証と呼ばない。

### AT-D04：実Windows入力・対象・緊急停止（#39）

- 前提：操作者がPCの前に常駐、Minecraft等を閉じ、疑似ゲーム画面を対象にする。未保存の作業を退避し、`Ctrl+Alt+F12`と物理キーボードを手元に置く。登録不能時は試験を開始しない。
- 操作：単一キー→左右マウス→相対視点→同時保持の順。保持中にPause、Alt+Tabで別の無害な画面へ移動、対象終了、PCアプリへ戻る、緊急停止、ホスト正常終了を個別に試す。非常停止後の再開は対象とモードを確認して明示操作する。
- 期待・合格：対象以外への押下なし。停止で全キー/左右ボタンを物理的に離し、視点も止まる。内部`down=[]`と疑似画面のkeyup/mouseup、実際のカーソル/キー状態が一致。各系列3回、残留ゼロ。失敗したら物理的にキー/ボタンを押し直して離し、安全停止して以降を保留する。
- SendInput失敗：アダプターの失敗注入はOSなしで別に実施。実OS失敗を起こすために権限・デスクトップ・保護機能を無断変更しない。内部状態だけで成功判定しない。統合済み#195の再解放・入力停止はローカルで確認済み。実OS側の残留状態は別に判定する。[変更別一覧](refactor-matrix.md)参照。

### AT-D05：Minecraft反復デモ（#40）

- 前提：AT-D02〜04合格、人が常駐。Java Editionの正確な版・ワールド・難易度・Raw Input・感度・キー設定、Reと操作定義のハッシュ、ネットワークを固定。バックアップから復元できる安全なワールドとホットバーを用意する。
- 操作：接続→分担→準備→Ready→移動/ジャンプ→視点→指定ブロックの破壊/設置→Pause→Resume→終了、を同じ台本で連続3回。3人全員が意味のある操作を行う。故障系列は混ぜず、失敗時は停止→原因表示→対象確認→再接続→明示再開の復旧を記録する。
- 期待・合格：連続3回完遂、入力残留・誤入力ゼロ。所要時間・成功数/試行数・全失敗と復旧時間を記録。安全停止の失敗は不合格とし、再試行成功だけで隠さない。ゲーム画面と端末操作が同期する動画（同意取得）を保存する。#40がclosedでも最新版の証拠がなければ未確認として扱う。

### AT-D06：配布・別Windows（#41・#148）

- 前提：開発環境のないWindows 11を1台用意。CI等で作った同一zipのSHA-256、展開ファイル、VC++ v14 x64とWebView2の有無を記録。既存の[構築手順](../handoff/SETUP_WINDOWS.md)と`package-smoke.mjs`を使う。
- 操作：まず不足環境の起動と案内を記録→人が公式必要物を導入→標準ユーザーで展開・起動・画面・終了→dry-runの静的配信→スマホ3台参加→監督下でAT-D04/05。オフライン時の必要物も事前に用意する。ファイアウォール変更は適用前後・承認・復元方法を人が記録する。
- 期待・合格：不足時に原因と対処が分かり、必要物導入後にアプリ/子ホストが起動・終了、孤児プロセスなし。3台参加とデモが成立。DLL/ブラウザ/ポート/配布漏れごとの結果を保存。開発PCやCIの成功を別PC合格に数えない。

### AT-D07：経路・遅延・障害（#157）

- 前提：同じ版・PC・端末・操作で、ホットスポット対ルーター、WS主体対RTC併用を比較。帯域・距離・混雑・Bluetooth条件は1項目ずつ変える。
- 操作：各条件60秒×3回の同じ単指入力・視点操作。通信診断・ホスト到着間隔・切断/復帰を記録。失敗/未成立の試行も残す。
- 期待・合格：サンプル数、p50/p95/p99、最大空白、200ms以上の空白数、切断数、復帰時間、主観操作性が揃い比較できる。USB結果は無線比較に混ぜない。往復RTT・ホスト内部時間・ゲーム応答を別列にし、時計未同期の差を片道遅延と呼ばない。性能閾値はこの資料で新設せず、実測とチームの許容判断を固定前に記録する。

### AT-D08：第三者試遊・本番復旧（#167）

- 前提：Minecraftを第一候補としてAT-D05合格後に実施。収録同意と公開同意は別に取得し、氏名や連絡先は公開記録に入れない。
- 操作：初見/経験者の別名3人に、説明→参加→1デモ→役割交換を行ってもらう。各自に「分担が分かる」「参加できた」「遅延が気になる」を5段階と自由記述で回答してもらう。障害役は人が明示して一度だけ通信断を作り、停止→案内→再接続→対象確認→再開を試す。
- 期待・合格：人数・経験・端末・成功/失敗・説明時間と復旧時間、各人の回答を残し、本番で見せる場面を決められる。少数の反応を市場需要や他タイトル互換性に一般化しない。復旧できない場合は安全停止し、事前収録へ切り替える条件を台本へ記録する。

## 11-12の固定判定（実施提案）

要件変更ではなく、実演可否を判断するためのチェック。安全停止の不合格・未確認を隠して固定しない。

- 同じコミット・配布物でAT-D02〜05が合格し、Android/iPhoneのAT-D01重点系列が揃う。
- 本番PCと予備PCのAT-D06、採用ネットワークのAT-D03/07、無線断時の復旧を確認する。
- 自動復帰の採用条件・デモ台本・予備映像・復旧担当を人が明示する。SendInput失敗の既知制約の扱いを判断する。
- 修正したら影響系列と安全停止、デモ3回をやり直す。凍結後の追加機能はこのGoalに含めない。
