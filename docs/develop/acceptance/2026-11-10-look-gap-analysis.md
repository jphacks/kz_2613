# 視点のホスト受信の空白の切り分け（#275、保存済み試行の再分析）

状態：PR #274 の実Wi-Fi試行（主21試行＋修正後6試行）の保存データを再分析した結果。新たな実機測定は行っていない。原因の一次切り分けであり、改善の実証ではない。

## 方法

- 対象：[主21試行](evidence/pr274-wifi/)（A〜E、A-ws、E-ws の各3試行）と[修正後6試行](evidence/pr274-wifi-after/)（E-after、E-after-ws）の `*.json.gz`。同一Windows・Android・Chrome、既存のWi-Fiホットスポット、dry-run。
- ホスト側：`hostInputTrace` の視点受信（`stage: received`、`lseq`・経路・`receivedUs`＝WS/RTCのコールバック時刻）。ハブの処理待ちは含まない。
- 端末側：`lookPerformance.times`（端末の `performance.now` による送信時刻）。全試行で `lseq` k の送信時刻が `times[k-1]` に対応することを確認した（`times` の長さ＝最大 `lseq`、epochは1つ）。
- 端末とホストの時計は同期していないため、直接の差を片道遅延としない。各パケットの「受信−送信」から試行内の最小値を引いた**相対遅れ**（最も速く届いたときより何ms遅れたか）だけを使う。
- ホスト受信の間隔が200ms以上の空白ごとに、①端末の送信時刻の最大間隔（欠落したパケットを含む）、②空白中に送ったパケットの欠落数、③空白直後に10ms以内で続けて届いた数（まとめ着）、④直後のパケットの相対遅れ、⑤逆順・経路の切替を求めた。
- 分類：端末の送信間隔も空白に近い→「送信側」、空白中に送ったパケットが直後にまとめて遅れて届いた→「遅着」、届かなかった→「欠落」、両方→「遅着＋欠落」。
- 再実行：`node scripts/device/look-gap-analysis.mjs docs/develop/acceptance/evidence/pr274-wifi/[A-E]-*.json.gz docs/develop/acceptance/evidence/pr274-wifi-after/E-after-*.json.gz`。結果は [gaps.json](evidence/look-gaps-275/gaps.json)。分類は合成データの試験（`scripts/device/look-gap-analysis-test.mjs`）で確かめた。

## 結果

| 項目 | 結果 |
|---|---|
| 200ms以上の空白 | 30件（主25件・修正後5件。Issue記載の件数と一致） |
| 送信側の空白 | **0件**。空白の間の端末の送信間隔は最大66.9ms（通常33ms、1周期の飛ばしまで） |
| 遅着＋欠落（RTC） | 20件。空白中に送った5〜9個のうち1〜2個が欠落し、残りが直後にまとめて届いた |
| 遅着のみ | 10件（RTC 3件、WS 7件）。WS（TCP）は欠落なし |
| 空白直後のまとめ着 | 3〜11個が10ms以内に連続到着 |
| 直後のパケットの相対遅れ | 135.6〜378.0ms |
| 逆順・経路の切替 | 0件・0件 |
| 空白中の欠落の合計 | 27個（RTCの試行全体の欠落は1試行17〜24個で、大半は空白と無関係な単発の欠落） |

## 解釈

- **事実**：空白の間も端末は送り続けており、そのパケットは空白の直後にまとめてホストのネットワークコールバックへ届いた。ハブの処理待ち（受信→受理は1ms未満、PR #274の計測）、経路の切替、逆順到着は原因ではない。
- **事実**：UDP（WebRTC、再送なし）とTCP（WebSocket）の両方で同じ形の空白が起き、UDPでは一部が欠落、TCPでは欠落なしで遅れた。
- **推測（未検証）**：両方式に共通するため、アプリの再送やRTC/WSの選択ではなく、無線区間（端末やホットスポットの省電力の受信待ち、無線の再送・集約、チャネルの混雑など）でパケットが滞留したと考えられる。どの機器のどの仕組みかは、このデータでは区別できない。
- 視点は累積値で送るため、欠落した分も次のパケットで取り戻す（最終位置は回復する）。ただし空白の間はPC側の視点が止まり、まとめ着でまとめて動く（ゲーム上の見え方は未評価）。

## 次の切り分け点

1. 端末の無線の省電力の影響：同じ条件で端末の画面常時点灯・Wi-Fiの省電力設定の違いを比べる（端末設定の変更は利用者の許可を得て行う）。
2. ホットスポット（PC）側の影響：別のローカルAPで同じ測定をし、空白の頻度を比べる（#156・#157）。
3. 送信の工夫の効果：RTCの生存確認 `ka`（協力プレイ中50ms）が空白を減らしているかを、送らない条件と比べる（製品の既定は変えない）。
4. 必要なら、同意を得た限定的なパケットキャプチャで、空白の間の無線フレームの再送・省電力の状態を確認する。

今回の分析だけでは原因の機器・仕組みを確定できないため、製品コードは変更していない。#264（状態送信・冗長同梱・バイナリ化）の採否もこの結果だけで決めない。
