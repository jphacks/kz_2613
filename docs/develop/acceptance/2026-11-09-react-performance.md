# PR #274のAndroid入力・通信性能比較

## 結果の範囲

同じAndroidでA〜Eを各3試行、入力60秒と視点60秒ずつ比較した。全15試行でボタンの論理入力224件をRustの受理ログと照合し、欠落・重複適用・未ACKは0。Pause・切断・回転・非表示・担当変更・再接続後に入力残留はなかった。両経路に同じiseqを送る仕様は維持しており、送信コピー自体をゼロにしたという意味ではない。

この条件では入力の大きな悪化や停止増加を観測しなかった。ただし数msの差を統計的な同等性や高速化の証明にはしない。主比較はCDP合成タッチとdry-runであり、実指・実OS入力・Minecraftの応答時間を測っていない。

| 条件 | 実装 | コミット |
|---|---|---|
| A | 移行前mainの静的JS | `c271ebe2335af9bdff5f30d58304a30d74f847f7` |
| B | PR内の静的JS | `9947391eb430dcc949877170e926b20e6a9d303b` |
| C | React UI＋JSエンジン | Bと同じ |

各対象は `data/local/review-baseline-main`・`review-baseline-pr`・`review-engine-ts`・`review-engine-async` のクリーンな独立worktree。測定後のReact資産ハッシュも測定時と一致することを集約スクリプトで確認した。旧ソース・素材を含む全配信資産のSHA256は各生データの `uiInventory` に保持する。

全15試行の共通ホストexe SHA256：`da1bdf8d0681281b669b9969211f02dcc70338ebf1873aefcf7a5ce429585668`。UI/エンジンの比較中にRustや通信アルゴリズムを変更していない。このexeは以前の検証用zipにも同一ハッシュで残っており、ローカルでは `data/local/pr274-review/baseline-host/` に保全した。標準URLの配信ルート変更後のホストは別ハッシュとして、標準化後の受入記録に分ける。

端末はAndroid 16 / SDK36、Chrome 156.0.8078.79、1080×2392・density450。PCはWindows 11 Home 10.0.26300（build26300）、x64、Core i7-1260P、論理CPU16・メモリー16GiB。同じPC・端末を使用し、電源/回転設定は試験後に復元した。端末serial・clientId・token・実IPは共有記録に含めない。

HTTP/WSはADB reverse TCP。RTCはローカルICE・STUN/TURNなしで成立したが、選択した候補対を収集していない。純粋なWi-Fi対USBの比較ではなく、RTCの経路内訳・帯域・距離・混雑・Bluetooth併用の影響は結論できない。旧補助CLIの「WebRTCはUSB経路」という説明はこの記録で訂正した。

## 試行と操作

A/B/Cは `A→B→C`、`B→C→A`、`C→A→B` の順。D、Eは実装後の追加点なので、その後に各3回実行した。全5条件を無作為な順に混ぜた実験ではなく、時間経過の影響を完全に除いてはいない。

各試行で専用ホスト・タブ・統計を新規生成した。2秒のタップによるウォームアップ後に生データ配列を空にし、48サイクルを同じ60秒の時系列へ配置した。単発、3回連打、1.2秒保持、同じボタンの2接点、異なるボタン、スティック8方向＋ボタンを各8サイクル。ジャンプ等の表示は実際のMinecraft実行ではなく、同じ操作定義を使った送信試験である。

続いて実回転・HOME/Chrome復帰・保持中のWebSocket close・再接続・再読み込み・担当変更を確認し、同じ視点担当で1800回の移動を60秒へ配置した。主比較はAndroid1台＋模擬P2/P3の3人配分で、視点担当には別ボタンがない。視点＋別操作は、標準化後の2人配分による補助試験で確認した。主比較で同時入力を行ったかのように扱わない。

前段の予備試行は時間内の反復で操作数が142〜144サイクルと異なったため採用しなかった。本比較のrunnerは `39e4c5d` 時点のv2。新しいrunnerには標準URL、2人配分、WS-onlyの補助検証も追加している。

## 観測値

単位はms。以下は各条件3試行のp95の最小〜最大であり、全サンプルを混ぜたp95ではない。各試行のn、p50/p95/p99/平均/最大、RTC/WS先着件数、最初/最後15秒、全生データは [trials.json](evidence/pr274-review/trials.json) と参照先のgzipを使う。

| 条件 | down→WS送信 p95 | up→WS送信 p95 | ACK観測 p95 | 視点送信間隔 p95 |
|---|---:|---:|---:|---:|
| A | 26.4〜27.2 | 24.5〜26.5 | 107.9〜108.9 | 34.8〜64.6 |
| B | 24.2〜26.7 | 24.6〜25.8 | 108.5〜108.7 | 35.3〜64.0 |
| C | 26.8〜28.1 | 24.7〜25.5 | 109.0〜109.1 | 35.1〜63.5 |
| D | 26.3〜28.0 | 24.0〜26.2 | 109.3〜111.5 | 43.0〜63.6 |
| E | 26.9〜27.8 | 24.7〜25.2 | 109.2〜111.3 | 63.5〜64.2 |

down/upは端末のPointerEvent時刻から同じ端末のWS send呼出まで。ACK観測はWS sendからブラウザーの受信listenerまでで、先に登録された製品ACK handlerの処理も含む。別々の端末/PC時計を差し引いていない。純粋なネットワークRTT、片道遅延、SendInput完了、ゲーム画面反映の値としては使わない。

Dで数ms高いACK p95を観測したため、受信処理がReactの診断描画を `flushSync` で強制する構造を除去し、Eを追加した。Eでも試行差は残る。同期描画を外した設計上の改善と、通信が速くなったという主張を区別する。

視点の平均間隔はA〜Eの全試行で34.48〜34.85ms、p99は約66ms。入力イベントがある周期だけ送るため、33msのタイマーが毎回パケットを出す保証ではない。CDP操作と送信タイマーの位相も含む。Dの最大は96.8ms、Eの最大は69.3msで、全試行の200ms以上の端末内送信空白は0だった。

ホスト `lookLost` は16〜21回。これは受信連番の空きで、遅着/逆順を含み得るため、実パケットの損失率や最終移動量の欠落と同一視しない。累積値で後続までの抜けを補う仕様はプロトコル試験でも維持している。最後のフレームが欠けた場合の完全な可視応答までは、この測定では保証しない。

最初/最後15秒のdown→send p95に一方向の共通した増加は見られなかったが、各区間のサンプル数は少ない。60秒を超える長時間劣化・電池温度・省電力による変化は未確認。

## 測れたものと残る計測点

| 項目 | 結果・限界 |
|---|---|
| down/up、ACK、視点周期と各分位 | 同一ブラウザー時計で計測。生データ保持。ACKには製品側受信処理が含まれる |
| ボタンの欠落/重複適用/未ACK | 各224件、全15試行で0。Rustの入力受理ログとiseqで照合 |
| RTC/WS先着 | ACKのviaを各試行に保存。両経路が成立した条件の先着比率であり、単独経路の速度比較ではない |
| 視点連番の空き | hostLookLostを保持。空きと不可逆な位置消失を区別する |
| 到着ジッター・受信後の順序保留時間 | 未測定。端末内送信間隔とホストの連番計数だけでは、受信間隔やibufの待ち時間を復元できない（#157/#264） |
| PC受信→入力受理 | 未測定。既存runtime-measureのWS queue指標は全WSメッセージの集計であり、入力/RTCだけの時刻対応ではない（#157） |
| 入力受理→物理出力 | 未測定。dry-runで実OS出力しない。最低押下・解放キューもあるため、ログの壁時計差を物理入力遅延と呼ばない（#157） |
| 通信断/復帰時間 | 主比較は全解放・同じ枠への復帰を確認。標準化後の補助試験ではPC側観測時間も追加した。CDP往復と100msポーリングを含む |
| 長時間・実指・Wi-Fi断・実ゲーム | 未確認。今回のPR標準化と製品全体の実機受入を分ける |

## 再実行と証拠

`scripts/device/android-dry-run.mjs` は明示したexeのSHA256を検証してからdry-run・設定なし・疑似対象で起動し、認可済みでロックされていないAndroid1台だけを対象にする。独立worktreeのソースと、当該版で生成したReact資産を使う。

```powershell
node scripts/device/android-dry-run.mjs --bin <共通ホストexe> --sha256 <そのSHA256> --adb <adb.exe> --root data/local/review-baseline-main --legacy --benchmark-ms 60000 --condition A-fixed --trial 1
```

Bはbaseline-pr＋`--legacy`、Cはbaseline-pr＋`--react`、D/Eは対応worktree＋`--react`。各3回、同じ端末/ホスト/操作で行う。`summarize-react-review.mjs` は成功したv2試行を一つずつ選び、資産・exe・端末・操作回数と入力照合を検証し、識別子を除いて共有gzipと索引を生成する。試行を混ぜず、失敗試行を成功試行で黙って上書きしない。

gzipはJSONで、`performance.raw` にイベント・送信・ACK、`performance.hostEvents` に該当試行の非注入入力/出力ログ、`lookPerformance.times/gaps` に端末内視点時刻、`hostRuntime` に既存ホスト集計を保持する。元のローカルsessionログは共有せず、gzipのSHA256を索引から検証できる。

## 標準化後の補助試験と試験コードの修正

配信対象はクリーンな `0d43517`、新ホストSHA256は `49800945fa52473c58a28ea8221e04f6b931b0e4162488ea97c28f5ef08a498b`。標準 `/` を使った。9個の製品JSのSHA256は測定済みEと全て一致し、入力製品コードを後から差し替えていない。補助runnerはメインworktreeから実行しており、記録中のsourceCommit/sourceDirtyは配信対象のworktreeを表す。

| 補助条件 | 結果 | 視点周期p50 / p95 / 最大 | PC側の全解放 / 復帰観測 |
|---|---|---|---|
| 標準3人、入力60秒＋視点60秒 | 全15項目合格、1800移動 | 33.0 / 63.9 / 68.3ms | 113.3 / 616.2ms |
| 標準2人、視点と別ボタン | 再試験で全15項目合格、1800移動中にattackを10down/10up | 33.0 / 50.2 / 115.1ms | 8.5 / 604.3ms |
| RTCを文書開始時に無効化した標準WS-only | 全15項目合格、path=WSのみ、視点は1.5秒の機能試験 | 33.0 / 63.7ms（主比較へ混ぜない） | 8.5 / 637.2ms |

上記の時間は同じPC processの観測時計。全解放時間にはCDPコマンド往復と最大100msのpollingを含み、3件の単発値から通信断タイムアウトの分布を推定しない。WS-onlyではダーク配色の入力OFFボタンも実画面で確認し、文字rgb(174,180,194)・背景rgb(51,56,69)、可視であることをassertした。Androidスクリーンショットを目視し、標準の操作面と無効ボタン表示を確認した。

2人同時操作の最初の2試行は `look companion down: 1 !== 10` で不合格だった。ボタン位置を毎回再取得しても同じ結果で、ホストログでは約60秒の一回の長押しになっていた。補助runnerが非空のCDP `touchEnd` に「残すパッド接点」を渡し、実際にはその接点を終了していた。[ChromiumのCreateWebTouchEvents実装](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/browser/devtools/protocol/input_handler.cc#600) で、非空リストは終了する接点、空リストは全接点の終了と確認した。

runnerを「終了するボタン接点id=2」へ修正し、10down/10upという合格条件は維持して再試験した。製品側の保持・送信コードは変えていない。失敗2件も[補助試験索引](evidence/pr274-review/standard-validation.json)と参照gzipに保存し、全試行でホストexit0・後片付け失敗なしを確認した。主比較15件の視点には別ボタンがなく、この不具合は発生しない。同一ボタン/別ボタンの主比較は終了順が逆でも両接点の押下・段階解放になっており、主比較の回数・受理照合を無効にするものではない。

今回の標準化は、この範囲で重大な入力停止・残留・表示回帰がないという判断による。実Wi-Fiの経路別測定、ホスト内の入力別時刻、受信ジッター/順序保留、長時間・実指・実ゲームの測定は引き続き未完了である。
