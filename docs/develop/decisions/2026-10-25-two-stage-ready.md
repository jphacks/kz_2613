# ゲーム準備と協力操作開始を分離する

2026-10-25のユーザー指示に基づく採用判断。以前の「接続人数が揃えばSTART」の記述より、この文書の二段階開始を優先する。

`lobby → preparing → coop → paused` とする。P1のPREPARE（旧STARTも同義）、またはPC画面の準備ボタンでpreparingへ移る。準備中はP2/P3の協力入力を受け付けない。P1がワールドを準備して明示READYを送ったときだけcoopへ移る。PCの監視接続からcoopを強制する操作は拒否する。

Readyには3人全員、利用可能な入力ドライバー、入力モードと対象の前面判定、緊急停止の登録が必要。dry-runの明示的な対象差替え試験だけは実ホットキー登録を条件にせず、OSへ入力を送らない。再開にも同じ条件と過去の明示Readyが必要。状態が古いPREPARE/READY/RESUMEはepochで拒否する。PAUSE/ENDは停止を優先する。

ゲームを開く処理は、許可された既存Minecraftのプロセス名とウィンドウタイトルを照合して前面化する。未起動・Windowsによる拒否は手動起動へ案内し、起動成功を捏造しない。実行ファイルの任意パス指定や一般ランチャー探索は導入しない（#49の残作業）。

通信契約v4で`canPrepare`、`canReady`、`canResume`、`hostReady`、`prepareStatus`、`readyReasons`を配信する。互換フィールド`canStart`は`canReady`と同じ。Node.js参照実装のv3は比較資料として残す。

ホストPAUSEは通信切断による停止と区別し、自動復帰を取り消す。15秒以内の復帰という過去の観測と、自動復帰の実運用の採用判断は従来どおり分離する。
