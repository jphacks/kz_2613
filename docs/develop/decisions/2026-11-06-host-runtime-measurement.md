# 本番イベントループと実WebSocketの負荷計測（#174）

[内部計測](2026-11-05-host-load-measurement.md)に加え、Windowsで製品版の `Hub::run`、実ファイルへのログ書込み、HTTPからアップグレードしたループバックWebSocketを使った。[計測結果JSON](../data/host-load/runtime-loopback.json) にexeのSHA-256と全10条件の集計を記録した。#157のスマホから実ゲームまでの遅延は別途計測する。

リポジトリのルートから `node scripts/sim/runtime-measure.mjs --bin <release exe> --duration-ms 5000 --out data/local/runtime-measure-results.json` を実行する。`--players 2,4` と全5条件が既定。子プロセスを `RECOOPLAY_DRY_RUN=1` と計測フラグで起動し、OSが割り当てたループバックポートを子自身の起動通知から取得する。各ケースの一時ログは `data/local/runtime-*` に残る。CIでは2人・通常・1秒をスモーク実行する。

| 条件 | 負荷 |
|---|---|
| normal | 参加者ごとに約33ms間隔で入力。協力開始後、視点担当が累積座標を送る |
| burst | 各接続で200フレームずつ送り、送信後に20ms待機。診断burstで監視ログの転送を抑える |
| slow-monitor | バーストと同じ件数設定で監視ログを転送し、追加の監視ソケットの読取りを停止する |
| disconnect | 通常負荷の途中で最後の参加者が切断する |
| many-log | バーストと同じ件数設定で監視ログを転送し、監視ソケットは読み続ける |

全条件でP1の保持出力を記録し、切断または緊急停止後に同じ出力の成功upを照合した。停止済み・全解放、旧epochへのstale ACK、新epochの非stale ACKを確認し、停止中の新規押下が注入されないことを検証した。

内部の時刻は単調時計を使用する。WSはテキスト化後にHubへ送る直前、停止はstdinのコマンドから停止イベントを送る直前が起点。Hubの処理時間・完了時間には計測集計のロック時間が一部含まれる。外部の停止時間はNodeのstdin書込みから監視側の状態受信までで、ソケットとクライアントの実行待ちも含む。ログ計測はJSONLへの記録と定期flushを分け、通知は監視向けシリアライズとキュー投入までを測る。

`ws_send_us` は成功・失敗を含むテキスト送信の完了値。`ws_queue_messages` は送信側が1件を取り出した直後の件数。`ws_send_pending_us` と `ws_queue_while_sending_messages` は同じ送信が未完了の間に20msごとに採った観測点。未完了観測は送信ごとの待ち時間分布と分ける。集計区間は起動から終了までで準備・停止後を含み、p50/p95は指標ごとの先着最大10万サンプル、最大値は全観測から計算した。各条件1試行で、観測値には計測自体の負荷も含む。

読取りを止めると、送信処理に5秒超の待ち、WS送信キューに8万件超の蓄積が再現した。一方、読み続ける別の監視接続では全条件で停止を確認し、Hub内の停止完了は今回の測定では最大1.480msだった。通常イベントのWS受信後のHub待ちは最大14.772ms。これは有限負荷の観測であり、無制限キューを持つ現行構成で安全イベント・通常イベントの有限の最悪時上限は保証できない。ボトルネックの発生箇所は送信先の受信停止と送信待ちで、Hub停止処理が同じ時間だけ塞がる現象は今回観測しなかった。配送保証の分類と背圧導入時の候補は[内部計測の判断記録](2026-11-05-host-load-measurement.md#配送保証と次の測定)を参照する。

実機のWi-Fi・RTC、Windows実注入、意図的に遅くしたディスクや標準出力の停止、持続的な過負荷、異なるPCでの最悪値は未検証。計測は送信待ちの特定と回帰の基準として使い、製品のキューや配送ポリシーの変更は別の判断とする。

## 送信キュー上限導入後の配送方針

[#239](https://github.com/jphacks/kz_2613/pull/239) で、参加者・監視のWebSocketごとに、送信中の1件とは別に送信待ちの本文を最大4096件にした。ACK、参加と担当、epoch、状態、操作結果、画面向けの入力表示・診断ログは同じキューで順に送る。状態を集約したり優先度で通知を選別したりすると、制御通知との順序を別に保証する必要があるため、上限を超えた接続は切断する。1件の送信が4秒で終わらない場合も切断する。切断は通常のホスト処理に渡り、参加者は再接続後に最新状態を受け取る。

この件数はアプリのWebSocket送信待ち本文の上限。終了などの制御フレーム、ソケットバッファ、セッションログのファイルは別に扱う。RTCの速達経路は主に端末からホストへの入力で、ホストからの `kpong` はDataChannelに直接送る。今回の負荷試験ではRTCのバッファと配送は計測しない。

### 2026-11-14の60秒追試

WindowsのPR #456配布ホスト（SHA-256 `ac9e097b0c997dce7964a14e1dd5de751afe6ebb4da7a17a75debaf3d3788e8c`）で、`--cases slow-monitor --players 2,4 --duration-ms 60000` を実行した。2人では755,600入力を送信し、送信待ち最大4096件、未完了送信の観測最大4,001,831µs、停止イベント投入からHub完了まで713µs。監視側でも停止状態を受信し、全解放と旧epochの拒否を確認した。

4人の初回は、読み取りを続けた監視ソケットが停止状態を待つアサーションでタイムアウトした。ホストのセッションログには `KEY_W` の解放成功と緊急停止による一時停止が記録された。監視側への配送と旧epochの拒否はこの試行では確認できなかった。

終了コードを記録できるようにして4人で再試行すると、監視側でWebSocketの異常切断（1006）を確認した。1006だけでは送信待ち上限と送信タイムアウトのどちらで切断されたかは分からない。2人・1秒の通常負荷は再試行後のスクリプトでも合格した。60秒の負荷は手動で実行し、CIでは既存の通常負荷を使う。

送信結果と上限超過を記録して再試行した。4人・60秒では読取停止側（接続6）は送信タイムアウトかつ上限超過、読取り継続側（接続1）は直前の送信が成功した状態で上限超過により切断された。接続番号は、この試験で監視1本、参加者4本、読取停止側1本の順に開いた順序に対応する。ホストログには `KEY_W` の解放成功、緊急停止と正常終了時の解放確認が残った。監視側での停止通知と旧epoch拒否の確認はこの試行でも失敗した。2人・5秒の通常負荷と監視読取停止は合格し、後者では読取停止側だけが送信タイムアウトと上限超過を記録した。
### 混雑時の入力診断ログ

入力ごとの画面向け診断ログは、監視接続の送信待ちが256件以上のとき、その接続への転送を省く。256件は、全体上限4096件の大半を状態更新・操作結果・解放通知などに残すための初期値。参加者宛のメッセージ、操作の表示イベント、保存用のJSONLは従来どおり扱う。低優先度メッセージ用の別キューは増やさず、送信対象に残った通知の順序を維持する。dry-run計測時は、接続ごとに省いた転送の合計件数を記録する。

変更後のWindows dry-runで、4人・60秒の読取停止条件が合格した。712,000入力を送信し、監視への転送を70,477件省いた。送信中の観測キュー最大は338件。読取停止側は送信タイムアウトで切れ、読み続ける監視は停止状態と解放通知を受信した。旧epochの入力拒否も確認した。実Wi-Fiとその他のメッセージ種別だけでキューが飽和する条件は未確認。
