# Windows入力アダプターの境界と失敗時の現行挙動（#170）

## 採用する境界

`InputAdapter: Send` は利用可否・理由、キー、マウスボタン、相対移動、ホイールの6操作だけを扱う。`Input` が従来のWindows/dry-run実装へ委譲し、`Hub` は `Box<dyn InputAdapter>` を保持する。フォーカス・認可・セッション・タイマー・ログはこの境界へ移さない。Win32の送信フラグ・引数、timeBeginPeriodの起動条件、プローブ用の既存APIも変更しない。

Hub全体を型引数で一般化する方法と比較し、通信やイベントループへ型引数を広げず、起動時に1つの内部依存を差し替えられるtrait objectを選んだ。仮想入力方式や製品依存は追加していない。動的呼出しの性能改善を主張する変更ではない。

## 試験用実装

`cfg(test)` の `RecordingInput` は、操作の引数・順序・成否を記録し、呼出しごとの成功/失敗を指定する。実OS入力を呼ばず、共有する観測ハンドルから要求を照合できる。既存#169のfixtureと回帰試験は保持し、利用不可、キー/左右ボタン/拡張スキャンコード/ホイール/リモコンの具体的な要求、部分失敗、視点失敗、連番消費を追加確認する。

## 失敗注入で固定した現行挙動と安全修正の条件

このPRでは挙動修正を混ぜず、以下を成功扱いではなく現行の特性として明示的に試験する。

| 再現条件 | 現行の内部結果 | 後続の評価 |
|---|---|---|
| キーdown送出がfalse | `physical` はtrueのまま。停止ではupを要求し、成否はinject.okへ記録 | 実OSでの失敗の意味と残留リスクを確認する |
| ボタンup送出がfalse、再び全解放 | 最初の停止で `physical=false`、次の全解放では同じupを再送しない | 解放再試行・不明状態の表現と上限を別安全修正で評価する |
| 全解放中の一部出力だけfalse | 残りの出力へのup要求は継続する | 後続の入力管理分離でも維持する |
| 視点移動送出がfalse | 未処理量と端数を消費し、診断集計にも送出量を加える | 再送時の重複や操作感と合わせ、診断の意味を別途判断する |
| リモコン移動送出がfalse | rseqを消費し、同じ番号を再処理しない | 通信上の先着1回処理と再試行ポリシーを混同しない |

up失敗後の再送なしと視点失敗時の消費は、失敗注入で内部再現できる。これは実際のWindowsで残留押下が発生した証拠ではない。対応が必要なら、失敗の分類、全解放の再試行上限、停止中の入力抑止、ログ/診断の意味を明示した独立の安全修正PRへ切り出す。#171の責務移動ではこの現行挙動を無断で直さない。実機の障害試験は[#39](https://github.com/jphacks/kz_2613/issues/39)を代替しない。
