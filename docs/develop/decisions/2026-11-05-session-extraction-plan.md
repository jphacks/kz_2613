# セッション判定の抽出設計と統合条件（#173）

## 状態と証拠の範囲

2026-11-05の監査。main `b3c0e88` の `hub.rs` と[通信仕様](../../protocol-specification.md)、#169の[PR #175](https://github.com/jphacks/kz_2613/pull/175)、入力境界の#181・所有管理の#185を照合した。今回は設計・試験系列の整理であり、セッション分離の実装完了を主張しない。製品コード・仕様は変更しない。

## 状態遷移・認可の実装上の条件

| 操作・境界 | 現行条件と結果 |
|---|---|
| PREPARE | lobby、P1接続、現在のゲーム・席順付きメンバーの決定が一致。P1のWS command、またはPC monitorのprepareから要求。preparingへ移りReadyを解除する |
| READY | P1のWS、preparing、現在epoch、ready_reasons(false)が空。必要時の前面化と実際のcan_inject成功後、設定再読込・参加者/分担固定・host_ready=true・coopの順 |
| RESUME | P1のWS、paused、過去の明示Ready、現在epoch、固定参加者全員・担当確認等の条件。前面化成功後に再開し、人数・分担を新規接続者で作り直さない |
| PAUSE | P1のWS、coopまたはpaused。自動復帰期限を0にしhost pauseへ上書き。既にpausedでも全解放・視点破棄・epoch更新・通知する |
| END | P1のWS、lobby以外。Ready・復帰期限を解除してlobbyへ。接続と席順は維持し、参加者/分担/決定は破棄 |
| OPEN_GAME | P1のWS、preparingまたはpaused、現在epoch。前面化要求でありReady・入力ONの代行ではない |
| 担当交換 | PC monitorから。lobby/preparingは接続者、pausedは固定参加者内の異なる2枠。全解放後にepoch更新、本人2名の確認が済むまでReady/再開不可。ホストはP1のまま |
| role_ok | 本人の現WS接続、現在epochのみ。自分の未確認を解除し、自動復帰条件を再評価する |
| 切断 | 枠とホスト権を保持。切断枠を解放。preparingは全解放・視点破棄・epoch更新。coopの固定参加者切断は全員解放してpausedへ。Ready後の非参加者切断ではcoopを止めない |
| 自動復帰 | check_targetを先に実行しPC画面への手動復帰を反映。paused・切断理由・ON・期限内（now <= until）・can_resume・全接続のRTC接続中解消が必要。前面化拒否は期限を0へ戻す |

PlayerのWS開始コマンドPREPARE/READY/RESUME/OPEN_GAMEだけにepoch一致を要求し、PAUSE/ENDは停止を優先する。PC monitorのprepare/open_gameはon_monitor_messageから直接commandへ入り、現行ではこのepoch照合を通らない。抽出時に両入口をまとめて無断でstrict化しない。実コードのcommand分岐にSTARTの別名処理はないため、古い二段階Ready判断の「旧START同義」を現行の期待値として追加しない。これは採用仕様の変更ではなく、過去記録と現コードの差の指摘である。

## 純粋判定と副作用の境界

抽出候補は `SessionFacts`（phase、P1/参加者の接続、lineup一致、担当確認、profile対応、入力可否、ホットキー、注入モード、Ready、切断理由、期限、RTC準備）から、要求可否・拒否理由列・遷移案を返す判定部。OS入力、前面ウィンドウ操作、時計読取り、ログ、通信、ゲーム検出を呼ばない。時刻は引数とする。

`ready_reasons(false)` はOnモードの前面化前の要求許可で、実入力許可ではない。`ready_reasons(true)` は拒否結果表示に前面不足も含む。両者を単一の「開始可」へ潰さない。拒否理由は現在の順序（参加者/人数・定義、担当確認、lineup、対象、操作対応、ドライバー、停止手段、注入/前面）と日本語文字列を比較する。

Hubには効果の実行を残す。通常のset_phaseは同phaseなら無処理。それ以外は全解放→視点破棄→phase/ロビー時の分担等更新→reason→epoch→phaseログ→低遅延モード更新→game通知の順。PAUSE再要求、担当交換、緊急停止、入力先喪失、release_inputsは別系列であり、同phase早期returnへまとめない。PREPARE/READYの設定再読込や分担固定はこの順序より前の独立効果として保つ。

## 実装時の試験系列

| 判定・効果 | 最低限の対照付き試験 |
|---|---|
| 準備と明示Ready | 人数2/3/4、未決定、決定後の参加者/対象変更、本人確認待ちを一つずつ変えて許可/拒否と理由列を照合 |
| 要求可否と実入力 | Onの対象非前面で要求可、前面化成功でcoop、拒否で停止維持。Off・入力不可・停止手段不足は前面化前に拒否 |
| 固定参加者 | Ready後の追加参加、固定参加者切断・復帰、非参加者切断、Pause中の人数再構成拒否を照合 |
| 自動復帰 | ON/OFF、期限の直前/一致/直後、P1断、複数断、replacedによる期限延長なし、RTC接続中/失敗、明示PAUSE/PC復帰/緊急停止の抑止 |
| 効果順序 | 記録アダプターでup/視点破棄/epoch/game通知の順と、旧Pump/旧epoch/未処理視点の非復活を確認 |
| 権限 | P2〜P4、未認証、旧WS/RTC世代、monitorのcoop強制を拒否。担当交換でホストを移譲しない |

#169/#170/#171の既存テストに加え、判定単体の全条件表と効果順序の統合試験を実行する。単体の可否だけで停止安全性全体の証拠にしない。

## 実装を再開する条件

入力アダプター・キュー・視点を同じHubから切り出すRust列は#175→#181→#185→#172の4段を安全な区切りとする。さらにセッション認可まで重ねると、親差分の変更が停止効果・epoch・ゲーム制御の評価へ波及するため、ここでは製品実装を保留する。マージ待ちだけを理由に全体を止めず、本監査と別領域のスマホ・計測は進めた。

再開には、先行PRのレビュー/統合でStackが短くなったこと、最新mainと親headの差分確認、#169〜#172のCI・失敗注入回帰成功、効果順序の基準固定が必要。外部担当のマージ後はまず判定部のみ抽出し、次に遷移効果の呼出しを移す小PRへ分ける。#179の型付き受信境界、#180のゲームサービス分離はこの境界の確定後に接続する。

実機のAlt+Tab・実ホットキー・無線断・ゲーム上の解放は#39の別受入であり、今回の設計やdry-runで合格扱いにしない。#161/#162の新しい役割・人数仕様を混ぜない。検証結果は[BUILD_LOG.md](../handoff/BUILD_LOG.md)へ記録する。
