# Rustホストの回帰試験と段階的分離の基準（#169）

## 判断と対象

2026-11-05のユーザー指示に従い、最新main `b3c0e88` を基準に、先に現行の入力・停止・通信の振る舞いを試験で固定する。#169では製品のアルゴリズム、定数、通信契約を変更せず、後続の責務分離で差を検出できる試験を補う。実行コマンドと結果は [BUILD_LOG.md](../handoff/BUILD_LOG.md) に記録する。

## 既存試験の監査と補強範囲

着手前の `hub.rs` と `input.rs` にRust単体試験はなかった。既存Rust試験は、操作定義・キー設定・ゲーム検出・入力先照合などを確認していた。`scripts/sim/protocol-sim.mjs` はRustホストをdry-runで起動し、以下を既に確認していた。

| 対象 | 着手前の証拠と補強する境界 |
|---|---|
| 人数・権限・状態 | 2〜4人、ホストのみの開始、担当外操作拒否、Ready/Pause/Resume/End、役割変更後の本人確認を通信試験で確認。現行の許可・拒否条件を維持する |
| 入力の順序 | 同じWebSocket上での重複、欠番、逆順到着を確認。WebSocketとWebRTCの両経路が共通の順序制御へ渡されたときの先着一回処理を補う。旧WebRTC接続世代の強い回帰試験は未実施で、後続の境界設計で扱う |
| 押下・解放 | 最低押下時間と各停止経路の全解放を確認。複数人の同一出力保持、最低解放時間、連打キュー上限と破棄順序、タイマー世代の無効化を直接確認する |
| epoch・再接続 | 旧epoch拒否、切断者以外を含む全解放、再接続時の旧押下非復元、自動復帰ON/OFF・期限・ホストPAUSEを確認。後続分離でも同じ条件を保持する |
| 視点 | 担当者制限とepoch間の累積値分離を確認。同epoch内の欠番回復・逆順拒否、整数化と端数保持、停止時の未処理量破棄を補う |
| 入力先・緊急停止・終了 | 模擬入力先の喪失・復帰、模擬前面化拒否、標準入力による緊急停止を通信試験で確認。終了の全解放は既存 `shutdown-sim.mjs` も証拠とする |

内部試験は実入力を出さない構築方法を使う。時間条件は可能な範囲で内部の経過時刻とタイマーを直接操作し、実時間の待機への依存を減らす。WebRTC経路の内部試験は、libdatachannelやスマホ実機による配送自体の合格を意味しない。

旧 `rtc_gen` の拒否は現行コードで確認したが、現行の所有接続確認は実際の `Peer` の存在にも依存する。今回のfixtureはlibdatachannelの生成を避けるため、有効世代なら処理され旧世代なら拒否されるという対照付き試験は追加していない。#170以降で接続世代の判定境界を検討する際の未検証事項として残す。

## 過去の記録と現行実装の区別

- 古い要件・案内にある固定3人・P1〜P3・固定操作名は現在の試験の期待値にしない。[2〜4人の判断](2026-10-25-variable-players.md) と [操作定義への統一](2026-10-26-unify-controls.md) に従い、現行コードはP1〜P4、Ready時の参加者固定、`act:<ID>` の分担を扱う。
- 開始は [準備と明示Readyの二段階](2026-10-25-two-stage-ready.md)。接続人数が揃ったことだけでcoopに入る期待値にしない。
- [自動前面化の判断](2026-10-26-auto-focus.md) により、開始要求の可否と実際の入力許可を分ける。前面化失敗を成功扱いせず、停止状態を維持する。
- 過去のNode.js試作品の観測や実演動画は保持するが、今回のRust版・現行コミットの受入へ読み替えない。自動試験はOS入力を無効にし、Windows実入力・スマホ・Minecraftの受入は [実機検証ゲート](../architecture/validation-gates.md) と区別する。

## SendInput失敗について確認できた範囲

コード上、`pump` は入力送出前に内部の `physical` を更新し、`apply_output` は送出の成否をログへ記録する。`look_tick` は `mouse_move` の成否によらず未処理量を消費する。現行dry-runは成功を返すため、この経路で失敗時の整合性を再現した証拠はない。実ゲームでの入力残留や安全不具合を実証したという意味ではない。

#170では記録・失敗注入可能な入力境界でこれらを検証する。問題を再現した場合は、再現条件と期待する安全動作を示し、リファクタリングと挙動修正を別PR・Issueとして扱う。#169で成功時の期待値を都合よく変更しない。

## 後続の責務境界と進行順

| Issue | 境界と維持すべき性質 |
|---|---|

| #172 | 累積移動・補間・整数化・端数を計算として扱い、出力量を入力アダプターへ渡す。4ms周期、係数、未処理量破棄と既存の診断集計を維持する |
| #173 | 状態遷移と権限判定を外部処理から分ける。全解放・視点破棄・epoch更新・通知の順序を維持し、新しい人数変更や役割仕様を混ぜない |
| #174 | イベント受信から処理、tick、ログ・通知、安全停止の計測を定義する。通常・バースト・送信停滞・大量ログを比較し、実測した問題だけ改善する |

実装PRは #169 → #170 → #171 → #172 → #173 の順で独立させる。先行PRの未マージ中は、同じ重要ファイルに分離実装を積み重ねず、次の境界の利用箇所・成功失敗時の状態更新・試験設計を監査する。mainへのマージとIssueクローズはユーザーの別判断を待つ。

#169の成果を踏まえた次の独立調査は、#170の入力呼出しと失敗処理の一覧化、および#174の計測値・配送保証・負荷条件の設計とする。無制限キューや同期ログは潜在リスクであり、計測前に実遅延や改善効果を断定しない。#174の計測実装を行う場合も専用Issueへの着手コメントと専用ブランチを先に用意し、`hub.rs` の競合変更を避ける。
