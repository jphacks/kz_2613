# 押下・解放・連打キューの独立core（#171）

## 責任境界

`input_manager.rs` の `OutputState` が、1つの出力の所有者集合、物理押下の内部状態、交互の押下/解放キュー、前回変更時刻、待機タイマー世代を管理する。OS、セッション、通信、ログ、実際のタイマー実行器には依存しない。

Hubは認可済みの操作を `set_holder` へ渡し、破棄した古い辺の組数を既存の `queue_drop` ログへ反映する。`pump_step` が返す `Emit` は従来の入力アダプター・ログ・モニターへ渡し、`Wait` はHubのタイマーへ予約する。`on_timer` は現在の世代だけ待機を解除する。`release` のtrueは、停止対象のup要求をその場で送る指示である。

Hubに残る出力配列は、操作と出力IDの対応・診断表示・アダプター呼出しのための入れ物であり、所有者やキューの変更アルゴリズムは持たない。フィールドは既存の回帰試験の観測と診断のためcrate可視を維持し、製品の状態変更はcoreメソッドに集約した。

## 明示時刻と副作用の順序

coreは時刻を引数で受けるので、最低押下60ms・最低解放50msの境界をsleepなしで直接検証できる。キュー上限8件、古い方から2辺の組を破棄する規則、所有者が残る間の押下維持を変更しない。

複数の出力指示をまとめて返す方式は選ばない。Hubは1件送出してから次の時刻で `pump_step` を呼ぶ。入力アダプターやログの所要時間がある場合も、固定した古い時刻で後続の辺を先行消費しないためである。待機時間からのタイマー予約、出力の内部状態更新→入力送出→ログ/通知、全解放時の出力番号順という従来の順序を保つ。

停止は通常の最低時間より優先する。対象所有者がなくなった出力のキューを消去し、予約世代を無効化して直ちにupを要求する。古いPumpが新たな待機を早期解除しないこともcoreと既存Hub試験で確認する。

## 検証と既知の失敗時挙動

#169と#170のHub回帰・失敗注入試験のアサーションは変更していない。新たな独立core試験6件で、複数所有者、正確な60/50ms境界、停止後のキュー非復活、部分/全解放の冪等性、最新8辺と破棄組数、旧タイマーの拒否を確認する。

[入力アダプターの判断](2026-11-05-input-adapter.md)に記録した、up失敗後に再送しないこと、視点失敗時にも量・診断を消費することはこの責務移動で修正しない。coreは送出成否を解釈せず、従来どおり内部状態を更新してから要求を返す。失敗分類と再試行上限・停止中の入力抑止を定めた独立安全修正で扱う。自動試験による内部再現と、実Windowsでの残留押下の証拠は区別する。

実行コマンド・結果は[BUILD_LOG.md](../handoff/BUILD_LOG.md)に記録する。Windows実入力、スマホ実機、Minecraftの操作感、実ホットキー、Alt+Tabはこの変更で新たに確認していない。
