# スマホコントローラーの個人レイアウトのデータモデル（#271）

- 日付：2026-11-11
- 対象：`apps/web/src/shared/model/layout.ts`、試験 `scripts/sim/phone-layout-test.mjs`
- 関連：#50（編集UI）、#272（型と境界の検証）、#235（React移行）

## 決めたこと

### 4つの関心事を分ける

| 関心事 | 持ち主 | このモデルとの関係 |
|---|---|---|
| 操作定義（どの操作IDがあるか） | ホストのゲーム定義 | 標準レイアウトの元になる。定義にない操作はレイアウトに残さない |
| 担当割当（誰がどの操作を使えるか） | ホスト（`assigned`） | 表示の絞り込みにだけ使う。送信の可否はホストが改めて判定する |
| 物理キー割当（PCへ何を送るか） | PCだけ（`key_overrides`） | 関係しない |
| UIレイアウト（位置・大きさ・表示） | スマホの中だけ | このモデル。**ホストへは送らない** |

レイアウトはスマホの中から出ないので、レイアウトを変えても、担当権限・送信先のキー・epoch は変わらない。担当外の入力は、今までどおりホストが拒否する。そのため、レイアウトのためのホスト側の検証は新しく足していない。

### データ（版1）

> 2026-11-14 に版2へ変更（`size` を `w`・`h` に分けた）。[新しい判断](2026-11-14-phone-operation-canvas.md) を参照。

```json
{ "schema": "recooplay.phone-layout", "version": 1, "game": "<操作定義のID>",
  "parts": [{ "id": "move:stick", "kind": "stick", "controls": ["act:forward", "act:left"],
              "x": 0.27, "y": 0.8, "size": 0.4, "hidden": false }] }
```

- 部品の種類は、現行の3種類（ボタン・スティック・視点パッド）だけ。新しい種類は作らない（Q05/Q18）。
- `controls` は送信と同じ `act:<操作ID>`（ホイールは `act:<ID>:up/down`）。視点パッドは担当の判定用に `look:<操作ID>`。同じ操作を複数の部品に割り当ててよい。
- 画面上の削除は `hidden: true` にする。操作定義は消さない。定義が変わっても「新しい操作」として復活させない。

### 座標はスマホ本体が基準（Q08〜Q10）

- 自然な向き（縦）に持ったときの**本体**の左上を (0,0)、右下を (1,1) として、部品の中心を置く。大きさは本体の短辺に対する比。
- 表示するときは `screen.orientation.angle` で回す。たとえば 90（反時計回りに90度）なら `画面 = (y, 1 − x)`。端末を回しても、部品は本体の同じ物理的な場所に留まる。
- 部品そのものは回転させない。そのため、ラベルは正立し、スティックの方向は表示中の画面の上＝前・右＝右になる。位置・文字の向き・入力の向きは、それぞれ別に扱われる。
- iOS の旧 `window.orientation`（−90）は 270 として扱う。

### 表示だけの一時補正（Q11/Q38）

- safe area からはみ出す部品と、重なって押せない部品だけを、最小限ずらして表示する（`placeParts`）。
- 補正は表示用の値だけで、保存データには書き戻さない。向きを戻せば、元の位置に戻る。
- 解消できない重なりは `conflict` として返す。確認の画面を出すのは #50 の役割。

### 定義変更との合成（Q04）

- 保存済みの部品は、位置・大きさ・表示・操作の割当を保つ。
- 今の定義にない操作は外す。スティックの方向が減っても、残った方向で位置を保つ。
- 標準にあって保存にない部品（新しく増えた操作）だけを、初期位置で足す。

### 保存（Q03/Q13/Q33）

- ゲームごとに1件、同じブラウザー・同じオリジンの `localStorage`（キー `recooplay.layout.<ゲームID>`）に保存する。
- 書くのは明示的に保存したときだけ。保存前に検証し、通った値だけを書く。
- 読み込みでは、構造・版・ゲームが違えば標準に戻す。個々の不正な部品は捨て、数値は範囲に収める。部品数は64までに制限する。保存先を読めないときも標準で表示する。

## 追記：編集画面とプレイ画面への適用（#50）

> **2026-11-14 に置き換え：** データは版2（幅・高さを別に持つ）になり、入口・編集画面・初期配置・未編集の人の描画を変えた。[スマホの操作画面と配置編集を同じキャンバスにする](2026-11-14-phone-operation-canvas.md) を参照。以下は当時の記録。

- **入口：** 協力プレイの画面のタイトル欄に「配置を編集」を置いた。押すと本人の押下をすべて離し、編集画面に切り替わる。編集中はコントローラーを実入力へつながないので、本人の操作はゲームへ送らない（Q12）。他の参加者には影響しない。
- **編集：** ドラッグで移動し（画面上の動きを本体座標へ戻す）、選んだ部品の大きさを変え、複製する（同じ操作を重複して割り当てられる）。画面から外した部品は戻せる。ボタンの操作は、自分の担当で今の定義にあるものにだけ付け替えられる。部品の種類は増やしていない。
- **確定：** 「保存して適用」で保存し、正式の表示に反映する。「変更を破棄」は保存せずに戻る。「初期配置に戻す」は保存を消す（Q13）。保存できないときは編集を続けたまま理由を示す。協力プレイの画面を離れたら、未保存の変更は捨てる（下書きの復旧はP3）。
- **適用：** プレイ画面は、**保存したレイアウトがあるゲームだけ**新しい配置で描く。未編集のゲームは従来の配置のままなので、編集しない限り Award Day のデモの見た目は変わらない。プレビュー（編集画面）とプレイは、同じ部品の描画（`PartFace`）と同じ位置計算（`placeParts`）を使う。
- **横向き：** 今の製品は横向きで「スマホを縦にしてください」と止まる（既存の方針、#52）。モデルと試験では横向きの配置を確かめたが、画面で横向きを使えるようにするには、この縦固定をやめる判断が要る。今回は変えていない。
- **確かめたこと：** 試験の撮影の仕組み（dry-run のホスト＋headless Chrome、402×874）で、協力プレイ→編集→ドラッグ・大きさの変更→保存→保存後のプレイまで動くことを画像で確かめた。編集中の送信数は 0。実機の指での操作・複数指・iPhone Safari は未確認。
