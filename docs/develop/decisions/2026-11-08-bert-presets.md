# 人数別プリセットをBERT風モデルで作る（2026-11-08）

## ユーザーの判断

- 「BERTのように、ゲームのプリセットを2〜4人のプレイヤー数に応じて適切に振り分けるものを作りたい」
- イメージは「ゲームプレイ前に2人用・3人用・4人用のプリセットがそれぞれ作られる」
- モデルは「Rustホストの中で毎回」動かす
- 「可能であれば実際のゲームのデータセットでやってほしい」「ローカルで読める情報の中でやってほしい」
- 学習は手元のPCではなくDGX（社内ネットワークのサーバー）で行う
- 「配布物(Tauri)がオフラインならよい」「ライセンスも学習に使うだけだから問題ない」「注釈はClaudeが付ける」：学習データ作りのときだけ GitHub の操作定義を集めてよい。集めたファイルはリポジトリに入れない（`data/local/`）
- 「オンラインにつながずに汎化させたい」に対し、Claude が実在のゲームの知識から学習データを生成する方法を選んだ（「あなたが実際のゲームから生成してほしい」「その感じで振り分けが出来るようにつくって」）

## 採用した構成（Claude Codeの提案。ユーザーは未確認）

- 学習データは実在のゲームだけにした。このPCのゲームのファイルから読んだ5本（Minecraft・Terraria・Goose Goose Duck・R.E.P.O.・Core Keeper）と、リポジトリの手作りの定義（9本と、上の5本のうち4本の手作り版）。合わせて14本・578操作。合成したゲームとジャンルの型の定義は学習に使わない。読み取りはインターネットを使わず、ゲームのコードも実行しない（`scripts/preset-model/build_dataset.py`）。
- 正解（操作がどの概念か）はClaude Codeが注釈した（`scripts/preset-model/data/labels.json`）。人の確認は済んでいない。
- 上の14本だけでは初めて見る操作名に弱かった（1ゲームずつ外した評価でカテゴリ69.0%）。そこで Claude Code が自分の知識から実在のゲーム79本のPCの初期キー設定を書き（`scripts/preset-model/data/claude-games.txt`、ネットもゲームのファイルも使っていない）、学習に加えた。評価に使う14本は書いていない。記憶から書いたので誤りが混ざる可能性がある。
- 交差検証の指標は、振り分けに使う操作（移動・視点・行動・持ち物）どうしの組で見る。UI・メニューの操作どうしの組が数を占め、プリセットに関係のない差で全体の値が動いていたため。
- 実データは少ないので、モデルを小さくし（2層・32次元）、BERTの穴埋めと同じ自己教師ありの課題（伏せたキーを、名前と周りの操作から当てる）を一緒に学ぶ。
- 推論はRustで直接書き、重みをexeに埋め込む。onnxruntime・candle等の依存は追加しない。
- モデルは「カテゴリ」「同じ人が持つべきか」「同じ軸か」だけを出し、2〜4人への組み立ては決まった手順（`preset_model.rs`）で行う。人が付けた分担の正解データがないため。
- 送ってよい操作は操作定義（役割案P1〜P3）が決め、モデルは誰が持つかだけを決める。
- ~~既定はモデル。`RECOOPLAY_PRESETS=rule` か、重みを読めないときは従来の規則に戻る。~~ **2026-11-13 の利用者の判断で置き換え：既定は規則で、`RECOOPLAY_PRESETS=model` のときだけモデル**（下の「2026-11-13〜14 の追記」）。画面には `game.profile.presetSource` で作り方を渡す。
- 組み立てのカテゴリの相性（`COMPAT`）は、3人で製品の基本の分担（P1移動・P2視点・P3行動）になるよう手で決めた。

## 未決・未検証

- モデルの案が実際に遊びやすいかは実機で確かめていない。Minecraft 3人は従来どおり専用画面（`fixedControls`）で、モデルの案は2人・4人に効く。
- 汎化の評価（`scripts/preset-model/README.md`）：操作定義の形（ホストが今モデルに渡す形）では十分に当たる（手作りの定義9本を1本ずつ外してカテゴリ97%・遊びの操作の同じ人の判定98%、ジャンルの型の定義381本でカテゴリ99.8%）。ゲームのファイルから読んだ生の名前では不十分（5本の平均でカテゴリ63%・同じ人84%・再現率72%）。
- 評価の正解も追加した学習データもClaudeが書いたので、数字が実際より良く出ている恐れがある。人による注釈の確認、実機での試遊、生データのゲームを増やすことが次の課題。
- ホストは初めて見るゲームのファイルを読まない（定義がなければ汎用の定義）。生データで振り分けるには、起動時にゲームを読む機能が要る。
- ホットバー10個のようにボタンの多いゲームでは、ボタン1つの重み（1）が実際の負担より重く数えられ、組み立てが負担の釣り合いに引っ張られる。重みの見直しは今後の課題。（GitHubのデータを加えた版では、Terrariaの3・4人用でカーソルが視点の担当になった）
- GitHubの注釈なしデータ（2,516本）は、振り分けの判断をほとんど改善しなかった。これ以上集めるより、注釈付きの生データと評価用のデータを増やすほうが効く。
- 注釈付きの生データ（GitHub 57本）は効いた（57本を4組に分けた評価で、再現率74.5%→83.2%、カテゴリ79.7%→85.8%）。注釈を足すのが最も効く改善策。乗り物系の再現率は39%で弱い。
- （解消）Forzaの3人用でアクセルとブレーキが分かれていたのは、乗り物系の注釈を足した版で直った。

## 人による評価と組み立ての修正（2026-11-13）

- 利用者が19本・43件（2〜4人で、規則とモデルの案が違うもの）を評価した（`scripts/preset-model/data/human-review-2026-11-13.json`）。モデルが良い30件・規則が良い11件・どちらもダメ2件。人数別では2人8/10・3人12/16・4人10/17で、4人で規則が選ばれやすい。
- メモで多かった指摘は「持ち物の切り替えだけ」「通報だけ」「マップ・メニューだけ」の担当では、することがないこと。モデルの判定（ツールバー1〜10は同じまとまり）は正しく、ボタンの数だけ重く数える組み立ての問題だった。
- 組み立て（`preset_model.rs`）を次のように直した。
  - 持ち物・メニュー・会話だけの自然なまとまりは、合わせて負担1と数える
  - 担当が持ち物・メニュー・会話だけになる人を作らない。その担当は相性のよい人に寄せ、遊びの操作を持つ担当を重い順に、することがない担当が出ず、カーソルとクリックも離れない形で分ける
  - 方向の移動（WASD・矢印・2軸）を持つまとまりを P1 にする
  - 操作定義の同じグループにあるカーソル（マウスの移動）とクリックは、同じ人に持たせる（Among Us）
- 既定は引き続き規則。2回目の評価を同じ19本で行う。

## 2026-11-13〜14 の追記（利用者の判断と実装）
- **既定は規則**。モデルで分担を作るのは `RECOOPLAY_PRESETS=model` のときだけ（11/08 の「既定はモデル」を置き換え）。
- **操作名の読み方を多言語 MiniLM の小型版にした版2**（#429・#430）。語彙を約4.4万語に絞り、重みを8ビットにして約40MB。重みは Hugging Face の公開リポジトリ（YOSHI0209/recooplay-preset-model-v2、CC BY-NC-ND 4.0）に置き、配布物の作成時に版を固定して取得・同梱する。Git には入れない。版2がないときは exe に埋め込んだ版1。
- **モデルが動くタイミング**（#431）：ゲームの一覧を読み込んだとき、プリセットのないゲームだけ1回作って保存する。状態を送るたびには計算しない。作り直すのはホストが明示したときだけ。
- **操作定義のないゲーム**（#431）：ファイルから操作を読み（Unity Input System・.NET の定義）、モデルで分類した仮の定義（未検証）と分担を作る。読めないゲームは従来の汎用の定義。
- **ホストが選ぶ**（#432、#58 の方針）：PC の分担画面で「規則／モデル」を切り替え、作り直せる。ロビーで決める前だけ。
- 学習データは公開リポジトリに置かない（履歴からも削除）。
