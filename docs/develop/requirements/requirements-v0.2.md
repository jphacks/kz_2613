## 0. 読み方・決定の扱い

- **[D] ユーザー確定**：このチャットで明示的に決定・採用した方針。要求の優先順位は最上位。
- **[M] 議事録由来**：「アイデア出し議事録」のチーム発想・候補。後の[D]と矛盾する場合は**[D]を優先**し、議事録案は追加・将来構想として残す。
- **[H] 仮決定**：実機検証、デザイン試作、実装結果で変更可。ユーザーの明示的な最終決定ではない。
- **[P] 設計提案**：実装上の安全性・成立性のための推奨。チーム合意未取得。

- **P0** はMinecraft3人デモの成立に必要、**P1** は優先的な体験改善、**P2** は製品将来像／今回のMVP対象外。**P0とP1を混同しない。**

## 1. なぜ作るのか／体験価値

### 1.1 問題と機会

- [M] 友達と集まり、誰かが一人用PCゲームを遊んでいる場面では、他の人は主に観客になる。
- [M] 既存のゲームを**新規ゲームとして作り替えず**、そのゲームの操作を複数人に割り振ることで、同じゲームを「一人の操作」から「みんなの協力」へ変える。
- [M] 協力の面白さには、操作が噛み合わず起きる笑いや失敗、声掛け、連携の上達、攻略時の達成感がある。**操作が全員の思いどおりに完全同期することだけが価値ではない。**
- [D] 単なるスマホ入力の集約だけで終わらず、**複数人が意味のある異なる操作責任を担う体験**を中核とする。

### 1.2 想定ユーザーと場面

- [M] 友人・家族・小グループで同じ場所に集まり、**同じPCゲーム画面を見られる人**。
- [D] MVPでは3人が1台のWindows 11 PCを囲み、一人のMinecraft Java Editionキャラクターを操作する。
- [D] 参加者のスマホはゲーム映像閲覧ではなく、**専用のコントローラー兼ホスト管理リモコン**に使う。
- [M] 遊び終わったら役割を交換して再挑戦したり、別のゲームを選ぶ。**役割交換自体はMVP P0ではない**。

### 1.3 プロダクトの独自性の仮説

- [D/M] 改造できない既存ゲームにも（対応する入力条件下で）協力操作体験を後付けする。
- [M] 人数とゲームの特性に合わせた分担を目指す。操作量や役割の重要性が偏らない設計を重視する。
- [D] Minecraftの最初の3分担は下記の固定プリセット。自動最適化・任意の役割交換は将来機能。
- [P] **対応可能な「任意のゲーム」を保証しない**。入力API、アンチチート、権限、ゲーム設定によって動作しないタイトルがある。「どんなゲームでも」は将来の方向性に留める。

## 3. 参加者・ホスト・役割

### 3.1 ユーザー識別と割当

- **ROLE-01 [D] P0**：空セッションの**初回接続スマホ**をホストかつ**P1＝移動**、次を**P2＝視点**、次を**P3＝アクション**とする。
- **ROLE-02 [D] P0**：ホスト自身も協力プレイの1人としてスマホから操作する。PC前でゲームを見ていることが前提。
- **ROLE-03 [D] P0**：共同プレイの**Startには3人すべての接続**が必要。2人以下では開始不可。4台目の新規プレイヤーはMVPの操作枠に入れない。
- **ROLE-04 [D] P0**：切断と再接続によって役割番号やホスト権限を自動的に割り振り直さない。ホスト自動交代なし。
- **ROLE-05 [H] P0**：参加時にセッション固有のランダムトークンを端末へ発行し、再接続は元の枠へ復帰。**同じ端末の物理的本人確認まではできない**ため、失効条件・ホスト再認証を別途設計する。
- **ROLE-06 [D/M] P1**：ホストによる参加者役割の指定、開始前／Pause中の変更・交換、役割表示と同意。
- **ROLE-07 [D/M] P2**：**2〜4人**の可変人数、ゲーム内容と入力負荷による自動役割分担、遊びごとのプリセット保存・交換。

### 3.2 Minecraft操作プリセット v0.1（ユーザー確定）

| 担当 | 入力機能 | Minecraftへの入力 | 指・操作特性 | MVPスマホUI |
|---|---|---|---|---|
| **P1：移動＋ホスト** | 前後左右 | W / A / S / D | 連続押下、同時2方向入力 | **十字キー P0**、仮想スティック P1 |
| P1 | ダッシュ | Ctrl | 移動と同時押下 | ダッシュボタン P0 |
| **P2：視点** | 視点の上下左右・照準 | マウスの相対移動 | 連続／滑らかな角度操作 | **方向ボタン P0**、領域内スワイプ P1 |
| **P3：アクション** | ジャンプ | Space | 短押し／連続押下 | ボタン P0 |
| P3 | しゃがみ | Shift | 押下／解放 | ボタン P0 |
| P3 | 攻撃・採掘 | マウス左ボタン | 押下／長押し | ボタン P0 |
| P3 | 設置・使用 | マウス右ボタン | 押下／長押し | ボタン P0 |
| P3 | ホットバー切替 | 数字キー1〜9 | 離散切替 | 1〜9直接選択または等価切替UI P0 [H] |

**操作負荷の設計意図 [D]：** 単純に「足・目・手」に分けるのではなく、移動と視点の継続負担を考慮して、ジャンプ・しゃがみをP3へ割り当てる。**負担が均等であると実測で確定したわけではない**。探索／建築／戦闘による操作量差は後に評価する。

**Minecraftキー設定上の注意 [V]：** `Ctrl`・`Shift`・マウス入力・物理キー解釈はMinecraft設定・版によって異なる場合がある。バインドが変わった場合にマッピング変更できる構造を設計するが、MVPでは既定設定／事前設定固定でも可。

## 4. ホスト専用PCリモコン

- **HOST-01 [D] P0**：ホストスマホは、**PC画面を見ながらPCアプリやゲームのメニューを操作するリモコン**になる。スマホ側に独立したゲーム一覧・PCゲーム映像は不要。
- **HOST-02 [D] P0**：最低限の入力は**方向キー4方向、Enter、Esc**。
- **HOST-03 [D] P1**：仮想タッチパッド／左右クリック／Eキー等を追加。PCゲームのメニューやインベントリの操作範囲を拡張する。
- **HOST-04 [D] P0**：ゲーム開始前・ゲーム内メニュー操作時・Pause後に**同じホストリモコンUI**を使い回し、スマホ画面遷移を減らす。
- **HOST-05 [D] P0**：ホストのスマホから**Start、Pause、Resume**を実行できる。COOP_PLAY中もホストの管理権は保持。
- **HOST-06 [D] P0**：Start後はホストの単独リモコン入力権を失い、ホスト自身がP1移動を担当する。Pauseすると単独リモコンへ戻る。
- **HOST-07 [D] P0**：リモコンは**PC側に映る画面を操作する**ため、PCのゲーム選択・Minecraftのメニューはキーボードだけで操作可能な範囲と、マウス必須の画面が混在する。
- **HOST-08 [H] P0**：MVPでは、ゲーム選択や起動を必要に応じてPC本体のキーボード／マウスで補助してよい。PCアプリのゲーム選択をキーボードフォーカスだけで完結させることはP1。
- **HOST-09 [H] P0**：Minecraftインベントリ操作に必要な完全なタッチパッド／Eキー／クリックはP0では保証しない。**P0のゲーム実演は事前に必要アイテムをホットバーへ準備**しておく。Pause後にホストが必要に応じてメニューに入ること自体はP0の操作モードで実現する。
- **HOST-10 [P]**：ホストリモコンの送信先が「PCアプリの選択UI」なのか「Minecraftの操作対象ウィンドウ」なのかを表示・管理する。スマホの独立画面遷移を増やさず、画面側フォーカスを管理する。

## 5. 画面・体験フロー

1. **PC準備 [D/H]**：Windows 11でPC側アプリを起動。Wi-Fi親機を用意し、ローカル接続用のアドレス・QRをPCに表示。Minecraft自体は手動起動でも可。
2. **スマホWi-Fi接続 [H]**：スマホ3台がPCホットスポットへ参加する。Wi-Fi接続用QRと、アプリ参加用QRは2段階になる場合がある。
3. **Web参加 [D]**：スマホの標準ブラウザでPC配信のWeb操作画面へ。参加順にP1ホスト、P2、P3。
4. **ロビー [H]**：自分の役割、参加人数、接続状態、Start可否を確認。MVPでは役割を動的変更しない。
5. **ゲーム準備 [D]**：ホストがPC画面を見て矢印／Enter／Esc等でゲームを選び、メニューを操作する。必要に応じてPC本体から手動補助。
6. **Start [D]**：**3人オンライン時のみ**ホストのStartが有効。ホスト単独操作→3人の役割分担へ権限切替。保持中入力は解放してから切替。
7. **共同プレイ [D/M]**：P1移動、P2視点、P3ジャンプ・ブロック操作。PC画面を見て声を掛け合う。
8. **Pause [D]**：ホストのPauseでRe:Cooplayによる**協力入力の停止**とキー解放。**Minecraftワールド内時間の停止ではない**。ホスト単独リモコンへ戻る。
9. **メニュー・管理 [D]**：ホストが必要に応じてEsc等を操作する。MVPで操作できないGUIはPC手動補助／事前準備で代替。
10. **Resume [D]**：ホストが明示的に再開。3人が接続済みであることが必須。古い長押し入力は継続せず、**新しい押下から開始**。
11. **切断 [D]**：P2/P3またはP1のいずれかが切れたら協力入力を**自動停止**。元の枠を保ち、3人が揃うまでは再開不可。
12. **ゲーム変更 [D]**：ゲームが終了・変更されたときはセッションとスマホ接続と役割を維持してホストのゲーム選択へ戻る。MVPではホストまたはPCから明示的に戻す操作で代替してよい [H]。

## 6. 状態機械と入力権限

### 6.1 状態

| 状態ID | 概要 | 許可する入力 | Start/Resume |
|---|---|---|---|
| `WAITING_HOST` | 起動後、まだ参加者なし | ゲーム入力なし | 不可 |
| `HOST_REMOTE` | ホストのゲーム準備、ロビー、ゲーム選択 | ホストだけがリモコン操作 | **3人接続でStart可** |
| `COOP_PLAY` | 3人共同プレイ | P1/P2/P3担当入力、ホスト管理のみ | Pause可 |
| `PAUSED_REMOTE` | ホストがPauseした状態 | 協力入力は禁止、ホストリモコンのみ | **3人接続でResume可** |
| `WAITING_RECONNECT` | 通常参加者が切断した状態 | 協力入力禁止。安全停止、ホスト管理 | 切断枠復旧後のみResume/Start可 [H] |
| `HOST_LOST` | ホスト通信断 | 協力入力・ホストリモコン停止／全解放 | ホスト権を復元後のみ操作可 [H] |
| `SESSION_CLOSED` | PCアプリ終了／明示セッション終了 | 全入力禁止・トークン失効 | 新セッションが必要 |

### 6.2 状態遷移イベント（提案）

```text
WAITING_HOST --最初のjoin--> HOST_REMOTE
HOST_REMOTE --3人接続+Host Start--> COOP_PLAY
COOP_PLAY --Host Pause--> PAUSED_REMOTE
PAUSED_REMOTE --3人接続+Host Resume--> COOP_PLAY
COOP_PLAY --P2/P3切断・タイムアウト--> WAITING_RECONNECT
COOP_PLAY --P1ホスト切断--> HOST_LOST
WAITING_RECONNECT --同枠再接続--> PAUSED_REMOTE [要ホスト再開]
HOST_LOST --同ホスト再認証--> PAUSED_REMOTE [要ホスト再開]
PAUSED_REMOTE --ホストがゲーム切替--> HOST_REMOTE
任意の状態 --PC上でSession End--> SESSION_CLOSED
```

- **SM-01 [D]**：PauseはMinecraftへEscを自動送信することを意味しない。
- **SM-02 [D]**：Pause・Start・Resume・切断時にキー／マウスボタンを解除し、過去の押下状態を引き継がない。
- **SM-03 [D]**：ホスト断で自動ホスト交代を行わない。役割順を変更しない。
- **SM-04 [H]**：切断が復旧しても自動でゲーム入力を再開しない。ホストから明示再開する。
- **SM-05 [P]**：状態遷移時に`control_epoch`（操作権の世代番号）を更新し、旧状態の遅延入力を破棄する。
- **SM-06 [P]**：端末がブラウザを閉じたりスリープしたりしても、サーバータイムアウトがあるので合成キーを永久に押し続けない。

### 6.3 権限マトリクス

| 権限 | HostRemote | Coop P1（ホスト） | Coop P2 | Coop P3 | PausedRemote |
|---|---:|---:|---:|---:|---:|
| ホスト単独の方向キー/Enter/Esc | **ホスト可** | 不可 | 不可 | 不可 | **ホスト可** |
| WASD・ダッシュ | 不可 | **可** | 不可 | 不可 | 不可 |
| 視点 | 不可 | 不可 | **可** | 不可 | 不可 |
| ジャンプ/しゃがみ/クリック/ホットバー | 不可 | 不可 | 不可 | **可** | 不可 |
| Start/Resume | ホストのみ（成立条件つき） | 不可 | 不可 | 不可 | ホストのみ（成立条件つき） |
| Pause | 不可 | ホストのみ | 不可 | 不可 | 不可 |

## 7. 機能要件：MVP P0

以下は**実装完了の意味ではなく、受入基準**。`FR`番号でテストと対応づける。

### 7.1 PC側・接続

| ID | 要件 | 受入・失敗時の扱い |
|---|---|---|
| FR-001 | PC側に1つのセッションを作成できる | PC画面に接続URLとQR等を表示 |
| FR-002 | スマホ3台がPCへローカル通信できる | 外部中継なしにHTTP表示とWebSocket送受信が成立 |

| FR-007 | 接続が4台以上になっても3人の権限が変わらない | P0では4台目の操作枠を与えず、拒否または見学不可の案内 [H] |

### 7.2 ホスト・管理

| ID | 要件 | 受入・失敗時の扱い |
|---|---|---|

### 7.3 Minecraftゲーム操作

## 10. 情報・通信・状態に関する論理仕様（実装技術は仮）

### 10.1 オブジェクト

- **Session**：`sessionId`, `status`, `epoch`, `createdAt`, `targetGame`, `hostSlot`, `slots[3]`, `startedAt`, `pausedReason`。
- **Slot**：`slotId`（P1/P2/P3）, `role`, `connectionState`, `resumeTokenHash`, `lastSeenAt`, `permission`。切断でスロットを削除しない。
- **InputState**：`heldKeys`, `heldButtons`, `lookDelta`, `lastSeq`, `lastInputAt`。**端末の役割単位**で管理し、実際のキーdown/upは中央の統合者だけが行う。
- **GameProfile**：Minecraft Java版のキー割当とUI操作を持つ。`gameId`, `supported`, `keyBindings`, `lookMode`, `launchTarget`。MVPでは固定値・手動設定でも可。
- **TargetWindow**：現在入力を与えてよいウィンドウの識別情報。PID/HWND等の識別が使えるかはWindowsで検証。

### 10.2 主要メッセージ（提案）

```json
{ "type": "hello", "session": "...", "resumeToken": "...", "clientVersion": "..." }
{ "type": "welcome", "slot": "P2", "role": "LOOK", "state": "HOST_REMOTE", "epoch": 4 }
{ "type": "key", "epoch": 5, "seq": 103, "key": "jump", "down": true }
{ "type": "look", "epoch": 5, "seq": 104, "dx": 12, "dy": -7 }
{ "type": "manage", "action": "pause" }
{ "type": "state", "status": "PAUSED_REMOTE", "epoch": 6, "slots": ["P1", "P2", "P3"] }
```

- `key`などは**クライアントが任意のWindows仮想キーを送る構造にしない**。許可された抽象アクションだけを送り、サーバーが役割・モード・キーへの対応を解釈する。
- `look`は**P2専用**。相対変位を送る。方向ボタン方式ではPC側で時間積分・一定感度の移動量を生成する設計 [P]。
- `seq`と`epoch`で旧セッション／旧モードの遅れたイベントを排除する。WebSocketは単一接続内の順序を保持するが、複数接続間の同時刻順序は保証しない。
- 押下・解放の**edge**イベントだけだとネットワーク切断に弱い。心拍、期限付き押下状態、明示的な全キーup、状態スナップショット等を併用する設計 [P]。
- UI・ゲームの技術スタック、IP、ポート、HTTP/HTTPSは実機検証で決められる仮設定である。

## 11. ゲーム選択・登録・起動の位置づけ

1. **P0 [D]**：PCにインストール済みのMinecraftを**ユーザーが自力で起動できれば可**。自動検出に失敗してもデモに影響させない。
2. **P1 [D/M]**：ホストがスマホリモコンから操作できる**PCデスクトップアプリ画面**で、手動登録されたゲームを選択する。必要ならホストがPC画面で手動操作を補助できる。
3. **P1 [M]**：Steam外のアプリ・自作ゲームの実行ファイル／ゲームプロファイルを登録する。
4. **P2 [D/M]**：Steamなどのランチャーメタデータ（インストール済みゲーム一覧、manifest、ゲーム実行情報等）とMinecraftランチャーの管理情報から、候補を自動発見する。API/保存形式/アクセス権・利用規約は個別確認。**PC内探索**でありインターネットWebクローリング必須ではない。
5. **[P]**：ゲームを検出できても、そのゲームに外部入力が通る、キーバインドを自動推測できる、アンチチートと共存できる、とは限らない。「発見」と「対応判定」を分離する。
6. **[P]**：ゲーム選択やUIのフォーカス切替中は**合成入力を全解放**する。スタート時には前面ゲームウィンドウが対象であることを確認する。

## 14. 推奨するシステム分割（要件から派生した設計案）

以下は**要件の確定事項ではなく実装の第一案 [P]**。技術検証によって差し替えられるように分離する。

```text
┌────────────────────────────── Windows 11 PC ──────────────────────────────┐
│ Minecraft Java Edition ──〔キーボード/マウス合成入力〕◀─ InputDriver      │
│                                                           ▲             │
│ Re:Cooplay PCホスト                                       InputEngine     │
│   ├─ セッション/参加枠/ホスト権限                            ▲             │
│   ├─ 状態機械/安全停止/入力リース                           State/Router   │
│   ├─ ローカルHTTP＋WebSocketサーバー ─────────────────────────┘             │
│   ├─ 静的Web画面配信、QR表示、PC診断画面                     │             │
│   └─ ゲームウィンドウ/入力プロファイル管理                    │             │
└─────────────────────▲────────────────────────────────────────────────────┘
                      │ ローカルWi-Fi（直接通信）
          ┌───────────┼───────────┐
          │           │           │
    iPhone/Android iPhone/Android iPhone/Android
       P1/Host        P2           P3
     React Web      React Web    React Web
```

- PC側候補：Python 3 + FastAPI WebSocket + Windows入力ドライバ（Win32 `SendInput`など）＋軽量デスクトップUI（候補：`pywebview` または最小ローカルUI）。**技術選定として未確定**。
- スマホ側候補：React + TypeScriptで役割専用Web画面を表示、ローカルPCからビルド済み静的ファイルを配信。**外部CDN依存なし**。
- WebSocketコマンドは状態・ロール・世代・シーケンスによりサーバー側で検証。
- 入力Driverはキー/マウスのdown/upを一元管理し、途中停止しても確実にupできる構造。
- `GameProfile`と`InputDriver`を分離すると、将来の複数ゲーム対応や注入方式変更に耐えやすい。

## 15. 開発・検証の順序（技術リスク順）

1. **V0**：Windows 11でMinecraft Java実機に、アプリからキー・左右クリック・**相対マウス移動**が反映するか最短スクリプトで試す。**最優先のGo/No-Go**。

## 17. 出典・情報の優先順位とトレーサビリティ

### 最優先：このチャットでユーザーが明示した内容 [D]

- Minecraft Java Edition / Windows11 / AndroidからデバッグしiPhoneにも対応／ローカル通信・クラウド非経由／PCホットスポット＋WebSocket仮決定。
- Minecraft用P1=WASD+Ctrl、P2=視点、P3=ジャンプ・しゃがみ・攻撃・設置・ホットバー。操作量重視。
- P1仮想スティック理想・D-pad最小、P2スワイプ理想・方向ボタン最小。
- 最初のスマホ参加者がP1とホスト、3人全員でのみStart、Start→分担、Pause→Re:Cooplay入力停止→ホストRemoteへ、Resumeまで共同入力禁止、再開時キー状態リセット、切断で自動停止、ホスト自動移譲なし、再接続でも枠固定。
- ホストスマホはPC画面に対するリモコンで、ゲーム前とメニュー操作時に同一操作画面を維持。最低は矢印／Enter／Esc、理想はタッチパッド／左右クリック。ゲーム変更後もセッションと役割保持。
- Steam／Minecraftランチャー情報によるゲーム自動検出・PCアプリ内選択を目指すが非コア。手動設定／自分でゲーム起動する方式でもMVP可。
- 初期Minecraftは3人、将来は2〜4人、PC画面共有・スマホに映像を送らない。
