## 1. 完成体験と決定済み仕様

Re:Cooplay：「**ひとりのゲームを、みんなの冒険に。**」既存のMinecraft Java Editionを改造せず、Windows 11で起動中の1人のキャラクターを3人のスマホで分担する。スマホはゲーム映像を配信せず、ローカルの入力端末になる。

- **3名・1ゲーム・固定分担（今回）**：P1＝移動／ジャンプ／スニーク／ダッシュ＋ホスト権限、P2＝相対視点ドラッグ、P3＝攻撃／使用・設置／ホイール／E／Q。
- **Readyを押すのはP1ホストだけ**。P2/P3の個別Readyは作らない。接続済みとReadyは異なる概念。画面の「準備完了」は**ホストの操作準備／ゲームの準備段階と開始条件**を正しく示す。
- **2段階開始：** ホストスマホでPCアプリの「ゲームを開く」（旧デザインSTARTに相当）を押す → Minecraftが前面になる／起動される → ホストがタッチパッドとクリックでゲームを準備 → **ホストが明示的に「みんなで操作開始」（Ready）** を押した時だけ3人分担操作に切り替わる。
- 「ゲームを開く」を押しただけで`coop`に入らない。Readyの前にP2/P3の操作を実行しない。P1の通常の移動担当もまだ開始しない。
- ゲームが起動していれば前面化を試みる。未起動時のゲーム起動は、安全かつ実装可能な範囲でローカルPC側の検証済み起動パス等を使う。**Minecraft Launcherを無条件で起動できる・ゲームが起動したと偽る・スマホから任意実行パスを送れる設計は不可。** 失敗時はPCでの手動起動／切替を明瞭に案内し、ホスト準備状態に留まる。手動フォールバックでもReadyまで到達可能とする。
- ホストのタッチパッドは、**PCアプリの操作**と**Minecraftのメニュー操作**の両方に用いる。操作先をウィンドウの信頼できる前面判定で排他制御する。左右クリック＋Esc／Enter／Eなど必要な補助操作を提供する。
- PCアプリの操作では、スマホからのリモートイベントをPC画面内の仮想カーソル／UI操作として扱う。Minecraft側では前面対象が検証できる時だけ必要なWin32 SendInputを使う。ホスト準備中だけ許可し、協力プレイ中にホストリモコンの通常操作を混ぜない。
- PC側の「ゲームを開く」は**ホストスマホから操作して押せる**必要がある。PC本体マウスでも操作可能としてよいが、P2/P3の権限にはしない。
- 協力プレイ中のホストPause、Pause後のホスト操作、明示Resume、END、フォーカス喪失、切断、緊急停止は既存の安全性以上に厳格。PauseはMinecraftゲーム時間を自動停止することではない。
- UIは提供画像にできる限り忠実に再現。PC UIとスマホUIは**同じデザインPRで同時に実装**。スマホ正式対応は縦向きのみ。横向きは安全に入力解放＋向き変更案内。
- ロゴ・キャラの正式データがなければ仮素材を差替可能な状態で用いる。ゲーム選択はMinecraft固定、操作割当は決め打ち。操作ボタン自由配置／色・文字・キー割当編集／役割交換／可変人数／任意ゲーム対応は今回追加しない。既存Issue（#47、#50、#53、#57、#60等）に将来機能として残す。

### 状態遷移の期待値

| 状態 | 操作できる人 | 入力先・権限 | 遷移 |
|---|---|---|---|
| `lobby` | P1ホスト | PCアプリの参加・選択操作。P2/P3は待機 | 「ゲームを開く」→`preparing`相当 |
| `preparing`相当 | P1ホストのみ | PCアプリ操作、Minecraftメニュー用マウス・補助キー。P2/P3とP1のcoop用操作は禁止 | P1の明示Ready→`coop`（条件成立時） |
| `coop` | P1/P2/P3各権限内 | Minecraftへの3人分担入力。ホストのPause等管理権は保持 | Pause等→`paused` |
| `paused` | P1ホストのみ | 全coop入力解放。ホスト操作／安全な復帰。既存の自動復帰条件は意図せず変更しない | ホストの明示Resume→`coop`、END→`lobby` |

`preparing`を独立Phaseにするか安全なサブステートにするかは、現在のRust hubに即して決める。ただし**権限・通信・再接続・表示から区別可能で、古い`START`がReadyを迂回して`coop`に入れない**こと。新しい画面段階とサーバーのゲーム進行を混同しない。

**`canStart`（現行は接続人数だけで真）を画面側の勝手なReady判定として使い回さない。** ゲーム準備可否・協力操作開始可否の意味をサーバーで分離し、必要なら`canPrepare` / `canReady`等を追加し、すべての画面に一貫して反映する。P1の通信断・画面復帰・ホストの明示Pause・自動復帰期限切れ・注入対象外ウィンドウ・緊急停止・未起動ゲームで勝手にcoopにならないこと。

## 4. 工程2：ホストのタッチパッド・クリック（機能PR2）

- Rustホスト`apps/host-rs/src/main.rs`の静的ファイル配信で、CSS/JSのほか PNG/JPEG/WebP/SVG/フォント（使う場合）の**正しいMIME**を設定し、相対URL・日本語ファイル名問題を避ける。`scripts/windows/package.ps1`の再帰コピーとビルド環境で、アセットが欠落しないことを確認する。
- UIのルートは静的HTML/CSS/JS。Web上で使うフォント等はローカル同梱か標準フォールバックを利用。外部CDNやランタイムのネット接続を追加しない。

**終了条件：** `colors.css`等が存在し、PC／スマホ共通で実色を利用し、元画像対応表と仮素材置換ルールがある。配布物からオフラインで読み込める。

**提出：** この工程をPR3の最初のコミット群として作成。PR2未マージならPR3のbaseはPR2のhead。**工程4に進んでからPR3を完成させる。**

## 6. 工程4：PC＋スマホUIを同時に実装（UI PR3の後半）

**Goal：** 完成イメージPNGへ可能な限り忠実な、操作可能で安全な全画面を完成する。**PC UIとスマホUIを別PRに分けない。**

### PC側（Tauri `/app`）

対象画像：`QRコード、人数表示.png`、`選択画面.png`、`分担.png`、`準備.png`、`準備完了.png`および背景素材。PC基準1920×1080、1280×720程度でも主要操作が隠れないこと。

- ロビー：Wi-Fi接続案内、参加用QR/URL、P1/P2/P3の3枠、接続/切断/再接続、端末種別、ホスト権限。元画像が2名分でも3名に適応。
- Minecraft選択：現行MVPで有効なMinecraft Java Editionだけを表示。将来ゲーム・ファイル選択が動くふりをしない。既存のMinecraft非公式製品表記を保持。
- 役割確認：P1移動・P2視点・P3操作の固定分担を可視化。今回は役割編集ボタンを実装しない。
- 準備：ホストがスマホでPC画面の「ゲームを開く」を操作可能。準備開始後もP1リモコンが有効で、P2/P3は待機。ゲーム状態は実際の`preparing`相当に同期。
- 準備完了／ホストReady：ホストだけが明示的に押す。**ゲームを開けたという表示と3人操作を開始できるという表示を分ける**。ホストReady後に`coop`へ入るまで嘘の成功表示をしない。
- `coop` / `paused` / error：安全な入力先、回線断、実際の停止理由、再開不可理由、緊急停止案内を表示。画面が戻った場合も参加者枠を保持。URL／QRはハードコードしない。

### スマホ側（通常ブラウザ `/`）

対象画像：`立ち上げ.png`、`接続完了1.png`、`接続完了2.png`、`PC操作(host).png`、`操作配置1.png`、スマホ背景等。縦402×874を基準に縦360幅級でも主要操作可能。横874×402の編集画像は**将来用の参考**とし、今回横画面UIを実装しない。

- 接続・割当：役割、接続状況、復帰、満員、通信契約不一致、トークン不一致を適切に案内。P2/P3はホスト準備完了まで待機。
- ホスト：タッチパッド、左右クリック、補助キー、ゲームを開く、明示Ready、Pause、Resume、End。ゲーム準備中はP1リモコンを表示し続け、ReadyでP1分担画面に移る。
- P1：仮想スティック、ジャンプ、スニーク、ダッシュ、管理のPause。P2：視点ドラッグと感度。P3：攻撃、使用、ホイール、インベントリ、破棄。**見た目を変えても操作メッセージ名と回数・押下時間・視点の累積送信規則を壊さない。**
- 各画面：切断、フォーカス不一致、長押し、pointercancel、画面非表示、回転時は安全解放。Safari/Chromeのsafe area、ブラウザバー、ホームインジケーターと操作が衝突しない。
- 将来のボタン編集画面を「動作する設定画面」のように見せない。今はMinecraft固定の操作配置をデータと表示に保持する。編集機能は#50・#53・#60の将来Issue。

### 画面とロジックの整理

- 接続管理、WebRTC、WebSocket、ロール・ゲーム状態、Pointer Events、30Hz視点送信、UI描画を適切なJSモジュールに分割。**高頻度の操作処理をDOM全体の再レンダリングや重いアニメーション処理に依存させない。**
- ブラウザ上の直接OS入力はできない。送信権限はRustで検査。PCの`remote`通知先はローカル画面のみで安全に使う。
- 素材の忠実性を優先し、可能なら実PC・iPhone/Androidのスクリーンショットを元PNGと並べて視覚比較、余白・背景・文字・ボタン形状を調整する。実画面を取得できなければHTML/CSSレイアウトを計測し未検証扱いとする。
- `host.html`診断画面、`game.html`疑似ゲーム画面は内部検証に利用するため削除しない。プロトコル版不一致・閉じたタブ・遅延時の挙動を損なわない。

**終了条件：** PC・スマホの主要画面が完成し、3名固定・Ready2段階・タッチパッド・役割操作・障害画面の表示／操作が成立する。元画像との相違・仮素材を文書化し、既存操作と機械試験が成功する。

**提出：** PR3：`codex/<ui-issue番号>-pc-mobile-redesign`。**base=PR2のheadブランチ**（未マージ時）。PR3はPCとスマホ双方の完成形を含む。**マージは禁止。**

## 7. 必須試験・パフォーマンス・回帰ゲート（各工程で実行）

- Rust：`cargo test` / `cargo build --release`（`apps/host-rs/`、`apps/desktop/`の適切な場所）、既存の手順に沿って実行。ロック済みビルド・Windows依存の条件に注意。
- Node試験：`node scripts/sim/protocol-sim.mjs`、`node scripts/sim/shutdown-sim.mjs`、`node scripts/sim/app-view-test.mjs`、`node scripts/sim/check-static-pages.mjs`、`node scripts/sim/input-probe-sim.mjs`。機能変更分の回帰テストを追加する。
- ゲート：P1以外のReady拒否、Ready前のcoopへの迂回不可、未接続／未フォーカス／注入OFF時の開始拒否、P2/P3のprep中入力拒否、切替前後の全キーup、epochの古い入力拒否、切断・再接続・自動復帰・ホストPAUSEで予期せぬ遷移なし。
- タッチ：PC画面カーソル／クリックとMinecraft用SendInputが混線しない。ゲーム以外のアプリへ注入なし。左右ボタン長押し・release・pointercancel・隠れタブ・端末回転・ホットキー停止が安全。
- 遅延：変更前後で`pointerdown→送信`と`pointermove→送信`（分布・p95を優先）、30Hz視点の送信間隔、WS/RTC入力欠落、長時間タスク等を可能な範囲で比較。**恣意的な「○ms保証」を新設しない。数値未測定なら未測定とする。**
- 画像：PNG/CSS/JS/フォント等のHTTP MIMEとキャッシュ、Windows配布ZIPでのローカル読み込み、ネット切断での表示を試験。重要ボタンが縦画面で可視・押下可能。
- 実機が使える場合だけ：Windows 11＋Android Chrome＋iPhone Safari（可能なら3台）で、Minecraftへの2段階移行／タッチパッド／Ready／Pause／End／緊急停止／フォーカス喪失を確認。使えない場合、工程0〜4の機械試験で実装を進め、**工程5以降の要実機項目として残す。**
- `docs/develop/handoff/BUILD_LOG.md`に**実行コマンド・実行環境・結果・未検証・証拠ファイル**を正確に追記。CIが失敗したら原因を調べて修正。CIが成功したことを実機合格と呼ばない。

### 重大不具合時の停止基準と復旧

- 認可を突破する、Minecraft以外へ意図しないSendInput、キー／ボタンが離れない、旧画面でReadyを迂回できる、回線断で誤入力が続く場合は**危険な状態で先へ進まず、その修正を優先**。
- 既存安定版を保持し、変更後に不具合があるならロールバック可能な状態にする。安全性を妥協して見た目だけ完成にしない。
- 全体の実機環境が無いことは作業停止理由にせず、明確に「未実機検証」と表示してテスト可能な部分の実装を進める。

## 8. GitHub IssueとPR作成ルール

1. 最初に既存Issueを確認。#46（タッチパッド）、#49（ローカル起動パス必要なら）、#51（QR・Ready案内）、#52（縦画面safe area）を適切に引用・更新する。
2. 新しい **2段階開始** と **PC＋スマホ合同UI刷新** のIssueが無ければ作成。余分な細分化・重複Issueを量産しない。可変人数#57、編集#50、プロファイル#60は将来Issueとして維持。
3. **PR1 → PR2 → PR3のStacked PRを実際に作る。** 各PRは完了条件・使用Issue・テスト・未実機検証・リスク・画面比較・次のPR依存を記載する。PR1へのユーザーレビュー待ちは理由にせずPR2/3まで進む。
4. 各PRは専用ブランチ、プッシュ・PR作成までは実施可。**マージ・auto-merge・main直接push・force push・不要なブランチ削除・Issueの無断Closed化は禁止。** `Closes #...`等の自動クローズ表記はマージ時に本当に完了するIssueだけに限定。未検証なら`Refs #...`とする。
5. スタックPRのレビュー差分が過剰に見えないよう、後続PRのbaseを先行ブランチにし、差分を整理する。通常の`main`からPR3を作ってPR1/2を再度含めない。
6. PRの作成ツール／権限が利用できない場合でも作業コミットを作り、`git push`やPRの作成を可能な方法で試す。作成できなかった場合は実行不能理由と、ユーザーが操作する最短コマンド・比較URLを最終報告する。作成済みと偽らない。
