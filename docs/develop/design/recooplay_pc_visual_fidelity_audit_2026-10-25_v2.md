## 0. 証拠と評価の限界

- 原案: ローカル `Recooplay素材.zip` のPC画像5枚（すべて1920×1080）を**原寸で視認**。Figma無料版の編集情報／正式フォント名は未取得。
- 現行: PR #92 の `apps/web-static/app.html`, `scripts/desktop.js`, `styles/desktop.css`, `styles/shared.css`, `styles/colors.css`, `styles/tokens.css`, `docs/develop/design/ui-reference-map.md`, および `docs/develop/design/evidence/pc-1920-preparing.jpg`, `pc-1280-preparing.jpg` を確認。
- **レンダリング画像で直接確認した現行PC状態は `preparing` のみ**。その他（参加、ゲーム選択、分担、Ready）は実装コードと画面構成から推定しており、視覚の最終評定は新規スクリーンショット取得後に実施する。
- 下の「一致度」は、色を使っていることではなく**領域、要素の位置、大きさ、フォント、視線誘導、情報密度**を基準とする定性的判定。恣意的な一致率（%）は算出しない。

## 1. 全ページ横断の結論

- **一致する要素**：白い左エリア＋黄色から桃色の星柄背景（背景2素材を再利用）、シアン/紫/クリーム系の色、白系の丸角カード、固定3役割という機能説明。
- **大きな不一致**：原案は「画面ごとに左の説明と右のメイン展示が**別レイアウトへ切り替わる5枚の演出画面**」。現行は「左に常駐3ステップナビ＋QR＋接続人数、右は管理画面の共通ヘッダー・phaseBannerとカード群」という**ダッシュボード**。`SCREENS=['join','game','roles']` の3画面しかなく、`preparing/ready` を`roles`にメッセージ追加して表示している。5ページの完コピにはDOMの状態別構成を変更する必要がある。
- **最重要変更**：デザインの絵を表層の色味として見るのをやめ、**ページ全体の情報設計を原案に合わせる**。右上ステータスや開発文言を追加して帳尻を合わせず、開発情報は `/host` に集約する。
- **先に守るもの**：2段階開始・P1だけのReady、3人固定、server-authoritativeな可否、host touchpadのPC/ゲーム排他、安全停止、WebSocket/WebRTC、v4のepoch認可、正しいQRと実接続表示、input modeへのアクセス手段。

## 2. 画面ごとの監査

### A. `QRコード、人数表示.png` → 参加画面 (`s-join`)
原案：左は「ろご」仮置き→極大シアンの「1人参加中！」→約250px幅の大きな`OK`の楕円→吹き出し「みんなのスマホで読み取ろう！」→大きいQR枠。右は上部に色つきの接続バッジ→プレイヤー名・機種を大きく表示する矩形情報カード→下に大きな縦長キャラクター枠。何もない星背景の余白も主役。
現行：左にはブランド／説明文／3段のナビ／QR／URL／Wi-Fi注記／人数／3行の接続説明が**同時常駐**。右は小見出し／説明文／P1-3の小さめ役割カードとボタン。**接続人数が主役になっておらず、原案のカード上部の状態バッジと縦長キャラ枠もない。**
判定：背景・配色は部分一致、レイアウト・文字階層・余白・キャラ枠は低一致。
改修：左の大きな数字＋「人参加中！」を最優先し、QRと短いCTAだけ配置。右は3人固定に合わせ**横に3列の上部情報カード＋下部縦長仮キャラパネル**。接続済み・待機・切断を色・文言で表示。QRのURLやWi-Fiの注意は条件が必要なときだけ小さく。ナビを左から撤去し、次画面導線を下部の小さな補助操作として保持。原案の`OK`は「準備できた」「次へ」等の実動作に接続し、押せない飾りボタンを置かない。

### B. `選択画面.png` → ゲーム選択 (`s-game`)
原案：左に黒の巨大2行見出し「ゲーム選択をしよう！」と細い横罫線。次に**大きく中央配置した短い説明**、下部にパス入力の存在を示すテキストと横長の楕円。右の約70%を覆う**薄いクリーム色の巨大1枚パネル**で、星背景が半透過して見える。リスト密集ではない。
現行：左は参加のナビとQRのまま。右には共通のヘッダー、説明文、小さいMinecraftカード（アイコン、手順リスト、注意バッジ）と遷移ボタン。巨大な1枚パネルの図形的インパクトを再現していない。
判定：背景・カードの角丸以外は低一致。
改修：左は画像に近い**ゲーム選択専用のタイトル、罫線、短い説明**へ差し替え。右は原案と同じ大型フレームを作り、Minecraft Java Editionの1タイトルだけを**ゆったりとカード化**（大きなタイトル＋ゲーム状態／最小操作）。詳細手順・Minecraft非公式の表示はリンク／折り畳み／小フッターに移す（削除しない）。原案の「任意パス入力」部分は今回は汎用起動に対応しないため**実装しない／飾り入力もしない**。必要なら「今回はMinecraftに対応」と代替表示する。

### C. `分担.png` → 役割分担 (`s-roles`, lobby)
原案：左中央に黒の大見出し「分担しよう！」＋罫線。短い2段説明。右の上段は**暗い半透明の大型の横長帯**（「○○を誰が担当する？」、右に操作サンプル E/W/Sの3段ボタン）。下段は**縦長の4人（仮配置）枠**、一人がシアンで目立つ。UIの主役はロール選択の演出。
現行：左は共通ナビ＋QR＋人数。右は3つの**横幅広め・高さ低め**のroleカードに記号・タイトル・細かな操作一覧、さらに下段に『ゲームを準備』『ゲームへの入力ON/OFF』という管理パネルを常設。
判定：3人の存在は表現されているが、画面構成・ビジュアル階層は低一致。
改修：**固定分担を維持する**ため、編集できる表示にはしない。右上の暗い横長の『3人で、ひとつの操作を分担！』等の演出帯と、見本操作チップを再現。右下は幅が均等な**3本の縦長キャラ・役割柱**に変更、役割名は大きく、説明は一言だけ。詳細キー割当と入力モード設定は本番の常時表示から外す。左は専用メッセージ、次に進む導線は視覚に溶け込ませる。

### D. `準備.png` → 準備中 (`phase=preparing` で `canReady=false` 等)
原案：左中央に**紫の特大「準備中…」**、直下に**グレーの無効START型CTA**。右には上部の状態バッジ・名前/機種カードと、下に大きな縦長キャラ枠が**二名分の想定**で並ぶ。画面は非常に疎、意味が即時分かる。
現行（実画面証拠あり）：左はロゴ→3つの長いステップボタン→QR→参加数と説明を常駐。右は`RE:COOPLAY / LOCAL CO-OP`ヘッダー＋『ゲームを準備しよう』、二つの状態ピル、横長のphaseBanner、詳細付きの3枚の役割カード、下部の「ゲーム準備」カードと「入力モードON/OFF」、戻るボタンと診断フッター。**原案の大型の紫タイトルも、左のdisabled STARTも、下に伸びるキャラ枠もない**。
判定：星背景と2カラム分割は一致、他のデザイン文法は低一致。特に情報量過多。
改修：`preparing`中の左画面は原案の紫タイトル＋大きなdisabled CTAへ切り替え、右上に3人分の接続状態、右下に縦長3キャラパネルとする。詳細な`canReady`理由、前面プロセス、inject ON/OFF、hotkey表示は**ユーザー操作が必要な警告だけ**本番最小表示。ホストスマホからReadyで協力開始するまで3人の協力コントローラに遷移させない。

### E. `準備完了.png` → 準備可能 (`phase=preparing, canReady=true`)
原案：左中央に**シアンの特大「準備完了！」**、その下に**水色輪郭・白背景の強いSTART型CTA**。右は全員『準備完了！』のシアンピル・プレイヤー情報カード＋縦長キャラパネル。参加と準備中と**同じキャラ位置**を維持することで変化が伝わる。
現行：個別画面は存在しない。`roles`内の小さな『✓条件が揃いました。ホストがReadyを押してください』へ変わるだけ。タイトルは`preparing`固定で『ゲームを準備しよう』。
判定：**画面固有の構図・強弱が未実装**。
改修：サーバーの`canReady=true`でPC表示が原案の準備完了画面へ自動切り替わる。左のSTART相当は**P1スマホでのみReady**という既決仕様を保ち、例えば楕円の文言を『スマホでSTART！』または『ホストがReady』とし、PCから協力開始できる偽ボタンは置かない。接続状態を『Readyを押した』と誤表示しない。`canReady`は『準備条件OK』、`hostReady`は協力開始済みと明示し、曖昧さを解消する。

## 3. 本番UI vs 開発UIの情報再配置

| 要素 | 本番PC | 開発/診断 `/host` | 理由・条件 |
| --- | --- | --- | --- |
| 参加QRと接続人数、P1-3の参加状態 | **参加画面で目立たせる** | 監視にも表示可 | ユーザーの次行動に直結 |
| 選択したゲーム、3人の固定分担 | **各対象画面で大きく** | 詳細キー割当あり | 視線と操作理解 |
| 『準備中』『準備完了』『協力中』『一時停止中』 | **大見出し** | Raw phase値も表示 | 原案の主役 |
| ホストの次の一手（ゲームを開く、Ready、Pause） | **短い導線のみ** | 実行状態詳細可 | 2段階開始は維持 |
| 前面アプリ不一致・入力が停止した重大警告 | **問題発生時のみ明瞭に** | `target`/`process`/`mode`詳細 | 意図しない誤操作を防止 |
| 緊急停止の案内 | **小さく常に見つかる位置** | hotkey登録成功/失敗と詳細 | 安全要件、完全には隠さない |
| 入力の ON/OFF切替 | **必要な管理導線は残すが常設大型カードを撤去** | 詳細操作・状態 | 単純に削除すると操作不能になる。すぐ見つかる詳細設定または管理パネルでアクセス可能にする |
| Wi-Fi注意・接続URL・QR関連 | **接続時のみ必要量** | IP/ネットワーク詳細 | 常設しない |
| 送信入力のログ・RTT・WS/RTC・注入詳細・target process | 原則非表示 | **開発用に保持** | プレイヤーに不要 |
| `mode:test`・疑似ゲーム・診断リンク | 本番の主導線から撤去 | **開発画面で保持** | スクリーン上の異物感を消す |
| Minecraft非公式製品表記 | **小さな補足または詳細でアクセス可能** | 同じく | 削除せず画面を圧迫しない |
| エラー・切断・QR失敗 | **必要時に簡潔表示＋復旧導線** | 診断原因・生ログ | エラー時の行動を可能にする |

注意：`/host`はPCローカル専用を維持し、診断や入力切替の権限境界を拡大しない。見た目だけ隠しても機能を失わせない。秘密情報・トークン・不要な端末識別値を本番画面に出さない。

## 4. 視覚仕様：完コピの具体的順序

1. **レイアウト先行**：1920×1080を基準に、白左パネルの境界（元画像の横約29.2%）、右側の背景画像原寸の切り取り位置と主要ビジュアルブロックを一致させる。元画像は2人／4枠の仮配置なので右内側を3人向けに等比再配置。新規要素で空白を埋めない。
2. **状態別左パネル**：共通の3段ステップナビ・QR常駐を廃止し、参加数／ゲーム選択／分担／準備中／準備完了でそれぞれ異なる「大きなコピー＋短い案内／CTA」を表示。共通ブランドは上部の小さな仮位置に保持し、原案の『ろご』をリテラル再現しない。
3. **右パネル**：参加→3人の色付き接続バッジ＋ネームカード＋縦長キャラ枠、ゲーム→1枚の大型クリームゲームフレーム、分担→半透明の横長帯＋3本縦長ロール枠、準備→同一位置の接続バッジと長いキャラ枠を維持。キャラは仮素材でも、**元案と同じサイズ／形／視覚的存在感のシルエット**にする。
4. **タイポグラフィ**：原案は左のメイン文言が大きく（72px級を候補として画像をピクセル計測）、黒・紫・シアン、白/灰のずらしシャドウ。現行の管理UI風な小見出し・英語eyebrow・多数の紫箇条書きをやめる。日本語フォントの実際の字形・太さを調べ、元案に近いローカル利用可能フォントを優先（外部CDNなし、権利確認なしにフォント配布しない）。
5. **UI部品**：白地に水色アウトラインの大きな楕円ボタン、上のカラー状態ピル、短い縦の矢印、プレイヤー情報カード、原案の半透明パネル、淡い影を再現。無効なら`disabled`/`aria-disabled`、状態が見える。
6. **動作と表現の一致**：`lobby → preparing → canReady → coop/paused` の画面遷移を機能と分離して表現。ホストP1スマホだけがReadyを実行し、PCのCTAは架空の開始権限をもたない。`PREPARE`/`OPEN_GAME`は許可された経路で操作可能。
7. **小画面**：1280×720で情報を詰めてしまうのではなく、原案の主役とCTAを維持。必要な詳細は明示的な補助ビューに退避。少なくとも重要な操作ボタンが表示され、巨大キャラは縮小・省略可能。
8. **色**：`styles/colors.css`を唯一のパレットに保つ。背景は原画像を活かし、白・薄青・紫・シアン・グラデーション／状態ピルの色を原寸画像のサンプルと突合する。CSSの新しい値を多重定義しない。

- `apps/web-static/host.html`：必要な詳細を開発用に退避（本番画面から安易に設定を消さない）。

## 6. 完了条件・禁止事項

- PC本番画面は原案5枚との対応が説明でき、同一条件の比較画像が5画面すべて揃う。背景だけでなく、領域面積・文字サイズ・配置・余白・枠・情報密度が近い。原案の2人/4枠は現仕様の3人へ適応した差分として列挙する。
- 本番に残る情報はユーザーの『今どの状態？・次は何をする？・誰が参加？・安全に操作できる？』が一目で分かる最小限にする。詳細診断は `/host` を優先。
- PC操作の仮想カーソル、ゲーム前面の制約、v4認可、Ready・Pause・緊急停止、診断画面アクセス、QR表示、配布ZIP、Android/iPhone画面を壊さない。新たなWS/protocol変更は可能な限り不要。
- 既存の`colors.css`/デザインアセットを活用。Reactへの全面移行、可変人数、自由操作配置編集は今回しない。
- 当日の実機検証を行っていない場合は未確認と明記。画像プレビューだけで実ゲーム成功としない。
- `main`の直接書換え、既存PRの勝手なマージ、auto-merge、Issueのクローズは禁止。既存の #92 ブランチをベースに**新しいフォローアップPR（stacked）**を作る。baseは`codex/89-pc-mobile-redesign`、先行PRのマージ後は適切に追従する。

## 7. 定量QAの提案（設計値ではなく比較方法）

- 基準1920×1080で各画面の左パネル境界、見出し矩形、CTA矩形、右のプレイヤー枠／ゲーム枠の矩形を抽出し、原案・実装の`x,y,width,height`を記録。
- DOMスナップショット上の主要要素のサイズ・色・フォントサイズ・太さ・影を表形式で記録。差がある場合は素材要件（3人固定、Ready P1のみ）に由来するものか、単なる未再現か区別。
- スクリーンショットで並列比較および50%透過重ね合わせ。アンチエイリアスや差し替えの内容に左右されるため、SSIMなど単一画像スコアだけで合格判定しない。
- 少なくとも5ページ×2解像度、および接続0/1/2/3人、準備前・準備中・準備可能、coop/paused、エラー表示を監査。

# 追加仕様：反復監査プロトコル（v2・最重要）

> **実装上の命令**：上の指摘一覧を一度修正するだけでは終わらないこと。**原案5画面に対して、実描画 → 採寸 → 評価 → 最重要差分の修正 → 再描画 → 再評価**を、合格まで必要な回数だけ繰り返す。監査を「最後に1回行う確認」ではなく、実装サイクルの中心に置く。
>
> **判断原則**：「デザイン原案の見た目を主軸にし、その中に最小限の必要機能を収める」。今の`app.html`の各カードやナビを温存するために原案の構図を崩してはならない。
>
> **確認不要の裁量**：既存のユーザー決定・安全要件・3人固定・P1のみReady・Rust認可を守る範囲で、要素の削減、文字の変更、レイアウトの書換、診断への分離は自ら判断して実装する。仕様不整合は記録した上で、既決仕様を優先。PRのマージ・main直接push・auto-merge・Issueクローズは行わない。

## A. 段階ごとのゴール

Codex環境で`set_goal`が利用できるなら、**自分で呼び出して**以下をゴール・サブゴールとして登録・更新する（利用できない場合は`docs/develop/design/evidence/pc-fidelity-progress.md`に同等の進捗を記録）。計画を表示するだけでは完了としない。

- **G1｜元画像の客観的仕様化**：5つの原案PNGを1920×1080で1枚ずつ実視認し、ページごとの文字列、要素一覧、x/y/w/h、背景・余白・フォント・線・影・色の推定値を記録する。`ろご`・`ここキャラ`等のプレースホルダーを識別。
- **G2｜情報設計の修復**：参加／ゲーム選択／分担／準備中／準備可能の5つを独立した*視覚状態*にする。本番用と開発用の表示要素を全数分類して適切に移動し、主役・CTA・情報密度を原案へ戻す。
- **G3｜原寸の完コピ**：5画面それぞれの1920×1080のスクリーンショットを原案と見比べ、構図、部品、文字、背景を収束させる。
- **G4｜小さなPC画面と動作の回帰**：1280×720、接続0/1/2/3人、切断、準備不可、Ready可、協力中、Pause、前面不一致、QR未取得等を確認する。操作や安全性を壊さない。
- **G5｜監査完了**：以下の*ハードゲート全部*、*定量・定性ルーブリック*、*反復ログ*、*スクリーンショット証拠*が合格状態になったことを確認してPR作成。

## C. 最初に守るハードゲート（1項目でもNGなら即不合格）

以下はスコア100点でも不合格にする条件。

1. **5状態が全部ある**：参加、ゲーム選択、分担、準備中、準備可能を**画面全体が変わる視覚状態**として実装。単なる同一ダッシュボードのタイトル変更ではない。
2. **意味の誤表示なし**：接続済みを個人Ready済みと表示しない。P1のみReady。PCで押せないSTARTを架空の有効ボタンとして見せない。ゲーム自動起動未成功を「起動した」と示さない。
3. **情報の混入なし**：本番に開発用の常時表示（英語eyebrow、ログ、RTT、OSプロセス名、詳細キー一覧、`inject`生設定、常設QR＋ステップナビなど）を詰め込まない。必要な画面で必要な情報だけ表示。安全警告は適切に残す。
4. **操作を失わない**：QR、画面遷移、ホストPC仮想カーソル、ホストReady、Minecraft前面化、入力ON/OFFにアクセスできる。権限・v4通信契約・epoch・フォーカス・緊急停止・入力解放を壊さない。
5. **原案5枚分の実スクリーンショット**：1920×1080の実描画画像が5枚。1280×720も5枚。プレビューの模擬データで撮影した場合は「表示確認用」と明記し、実バックエンドでの機能確認を偽らない。
6. **表示不備ゼロ**：重要な見出し・CTA・接続状況が欠けない、重ならない、誤読を誘わない。コンソールに未処理例外・アセット404がない。QRは本番では実データ、テストで代用した場合はラベルで区別。
7. **画像の改ざんなし**：デザイン元PNGを証拠画像として保管し、比較のために勝手に修正・トリミング・解像度変更して原案との差をごまかさない。許容差のための差分マスクは**小範囲かつ理由と矩形を明示**。
8. **既存自動テスト/配布**：関係するRust・Node・Web表示・静的配信・配布試験が回帰していない。Windows/実機のみの制約は正確に「未検証」とする。

## D. 各ページ100点のルーブリック

採点は必ず**5ページを個別**に行い、画像・寸法・CSSの根拠を添える。重みは視覚的な重要度を反映している。内部機能の安全確認は上記のハードゲート側で扱う。

| 観点 | 配点 | 合格を示す具体的な証拠 |
| --- | ---: | --- |
| ① ページ構造・情報階層 | **25** | 原案の「左が大きなコピー、右がビジュアル」構図／各ページ固有の主役／説明が少ない余白の活用を再現。3画面ダッシュボードから脱している |
| ② 位置・寸法・余白 | **25** | 左右境界、巨大タイトル、CTA、主要カード、キャラ枠を計測。原案との矩形差分を記録し、3人化例外を除き近い |
| ③ タイポグラフィ | **20** | 字形・和文フォント傾向、太さ、サイズ、行送り、改行、字間、影、文字配置を1要素ずつ評価。全ページで統一されている |
| ④ 形状・装飾・配色 | **15** | PNG背景の使い方、輪郭線、ピル、楕円、半透明帯、影、青・紫・クリームの実測HEXを一致方向に調整 |
| ⑤ 情報密度・演出意図 | **15** | 本番視聴者が3秒で状態と次の一手を理解できる。開発情報が画面を圧迫しない。元の余白を再現し、無意味な説明が増えていない |
| **合計** | **100** | **全5ページで95点以上かつ各観点80%以上**を目標にする。理由なく点数だけつけない |

### 位置・文字の客観的な目安

1920×1080での原案→実装比較。これらは**ユーザー要求から導いたQA目標値**であり、原案に最初から書かれた公式仕様ではない。適応が必要な場合、該当要素だけ例外登録し、見た目の同等性を別途説明する。

- 左の白パネル境界：元の背景素材幅**約561px**（1920幅の約29.2%）を基準。再現に必要な主領域の境界位置は**±12px以内**。
- **主要5要素**（ページタイトル、主CTA、右の最大パネル、プレイヤー情報カード群の外接矩形、キャラ枠群の外接矩形）：対応要素の中心座標 **原則±24px以内**、幅・高さ **原則±5%以内**。**3人の再配置は別枠で外接矩形全体のバランスを比較**。
- 主要見出しの文字サイズ：測定できる場合は**±8%以内**（字形差を考慮）。改行数と視認上の行揃えはなるべく一致。文字の影、字間、色も採点に含める。フォント名が特定できなければ近い字形を試し、独断で「完全一致」としない。
- 塗り色・輪郭の基本カラー：**元PNGのサンプル位置を併記**。図形のベタ塗り部分は可能ならHEXで正確に合わせる。グラデーション・半透明部は背景の切り取り位置を含めて視認比較する。
- **最上位のCTA・状態説明**：模写して装飾ボタンにしてはいけない。押下可能なら現行仕様の実動作、不可なら明確な無効状態／案内とする。
- 1920×1080を優先するが**1280×720で文字・ボタン切れゼロ**。後者の寸法を無理に原案へ合わせる必要はない。大画面の完コピと小画面の使いやすさは別採点する。
- ピクセル差分・SSIM等は**補助指標**とし、アンチエイリアス・ダイナミック文字・3人枠変更の差があるため、それだけで合否を判定しない。スコアの根拠に比較画像と矩形差分の表を必ず使う。

### 優先度分類

- **P0（機能・安全）**：操作不能、誤操作、架空のReady、入力先誤認、緊急停止やQR破損、実装したはずの画面欠落、テスト退行。直ちに修正。
- **P1（デザインの根幹）**：5ページ構図が違う、左側がナビに占領、見出しが小さい、右側が管理カード群、キャラ枠や巨大ゲーム枠が欠落、原案と全く異なる文字量。**1件でも残ればデザイン未完成**。
- **P2（細部）**：線太さ、影の濃度、ボタン曲率、文字間、アイコン形、局所の位置・寸法・彩度の差。全5画面95点を目標に継続調整。
- **許容された仕様差**：原案2人/4人→固定3人、プレースホルダーの正式素材差替待ち、P1だけReady、Minecraftのみ、開発情報の別画面移動。差分レジスタに理由と実装への影響を記録し、未再現の免罪符にしない。

## E. 自律・無制限の修正→監査ループ

以下を**毎サイクル**実行する。1〜3回だけで妥協して終わるような回数上限は設定しない。ただし環境限界で本当に継続不能なら事実を報告し、成果を残す。待機・確認依頼を理由に可能な作業を中断しない。

1. **撮影**：原案の5枚を原寸で開き、同じ1920×1080・ページ状態の製品HTMLをレンダリングしてPCスクリーンショット5枚、加えて1280×720を5枚作成。静的プレビューを使用する場合は明示し、バックエンド連携試験と区別する。
2. **比較画像生成**：原案／現行を左右に並べる。必要なら原案50%透過オーバーレイと領域マーカー（枠・タイトル・CTA）の重ね合わせも作成。比較画像と元の生スクリーンショットを両方残す。
3. **計測**：主要領域の`x/y/width/height`、`getComputedStyle`の`font-family/font-size/font-weight/line-height/letter-spacing/background-color/border/border-radius`を取得。画像の原案座標は実測・視認による推定の区分を明示。
4. **差分登録**：画面ごとに「原案、現行、見た目への影響、P0/P1/P2、根拠、修正手段」を記述。ページ別の採点とハードゲート判定を更新。
5. **修正**：P0 → P1 → P2の順。同程度の優先度では「情報構造 → 配置 → 文字 → 形状 → 色」の順。管理用要素を残すために原案の主役を小さくしない。
6. **回帰試験**：変更後に構文・画面ロジック・PC仮想カーソル・サーバーの状態表示・通信/操作経路を確認。表示中の操作が意図どおり働くか確認。エラーを新たに発生させた場合は修正してから次へ。
7. **再撮影・再採点**：**修正前の比較画像と並べ**て改善があったことを記録。点数が上がったように見えても構造不一致や機能退行があれば失敗とする。
8. **ゴール更新**：`set_goal`があれば更新し、次の最大差分を自分で決め、続ける。`set_goal`がなければ進捗MDへ「サイクル番号、残差分、今回の修正、点数、証拠へのパス、次の対象」を追記。

**終了条件**：以下のすべてが揃った場合にのみ「PC UI原案一致度の監査合格」と書いてよい。

- 全ページ**95/100以上**、かつ各観点**80%以上**、P0/P1残件0、ハードゲート全部PASS。
- 1920×1080の5枚・1280×720の5枚が存在し、原案5枚との対応とデザイン差分（仕様によるものを含む）が説明できる。
- 最後の修正後に**連続2回**の独立した再撮影・再監査で全合格条件を維持する（同じ画像ファイルを名前だけ変えて流用しない）。
- スタイル変更で安全・通信・Ready・QR・前面化・操作性の回帰がないことを、実行可能なテストで確認。実機固有の項目は未検証と明記する。
- `docs/develop/design/evidence/pc-fidelity-progress.md` に各サイクルと最終残差分を残す。**未解決項目があるなら「完コピ完了」と報告しない**。

### 点数を高くするための誤魔化しを禁止

- カードを白背景＋シアン枠にしただけで90点以上にしない。**原案では巨大な演出要素が主役なのに、現行が管理表主体なら構造25点は大幅減点**する。
- 原案の重要要素を削り、比較対象が減ったからといって「一致」としない。**原案のすべての主要要素に1対1の対応先**が必要。
- 左列境界が一致するだけでレイアウト一致にしない。**左右パネルの内側**が一致しているかを見る。
- 2人・4人→3人の仕様適応を口実に、巨大タイトルや大型キャラ枠の寸法不一致を許容しない。
- 画面内に存在しても折り畳みやスクロールの下で主CTAが見えなくなるなら不合格。
- Figmaや正式フォントを取得できなければ、PNGから測った範囲で最大限再現し、正確な限界を記録。「完全一致」という保証を捏造しない。
- 合格点を満たさないのに、Issue/PR作成、CI成功、レンダリング1枚の確認を理由として完了としない。
