## 0. 読み方・決定の扱い

- **[E] 実機検証済み**：試作品で実装し、Windows 11とスマホ3台の実機で動作を確認した。[D]と矛盾する場合は**[E]を優先**する。
- **[D] ユーザー確定**：ユーザーが明示的に決定した方針。
- **[M] 議事録由来**：チームの「アイデア出し議事録」の発想・候補。[E]・[D]と矛盾する場合は将来構想として残す。
- **[H] 仮決定**：実機検証、デザイン試作、実装結果で変更できる。
- **[P] 設計提案**：安全性・成立性のための推奨。**未実装なら課題として扱う**。
- **[V] 要検証**：実際にできるかは保証しない。
- **P0**はMinecraftの3人デモの成立に必要、**P1**は優先的な体験改善、**P2**は将来像でMVPの対象外。

**v0.2からの主な変更：** 技術構成（Rust、WebSocket＋WebRTC）、Minecraftの操作割当（ジャンプ・スニークをP1へ、ホットバーはホイールへ）、進行の状態（3状態＋停止理由）、切断からの自動復帰、入力の時間処理、視点の送り方。

## 1. なぜ作るのか／体験価値

### 1.1 問題と機会

- [M] 友達と集まり、誰かが一人用PCゲームを遊んでいる場面では、他の人は主に観客になる。
- [M] 既存のゲームを**新規ゲームとして作り替えず**、そのゲームの操作を複数人に割り振ることで、同じゲームを「一人の操作」から「みんなの協力」へ変える。
- [M] 協力の面白さには、操作が噛み合わず起きる笑いや失敗、声掛け、連携の上達、攻略時の達成感がある。**操作が全員の思いどおりに完全同期することだけが価値ではない。**
- [D] 単なるスマホ入力の集約だけで終わらず、**複数人が意味のある異なる操作責任を担う体験**を中核とする。

### 1.2 想定ユーザーと場面

- [M] 友人・家族・小グループで同じ場所に集まり、**同じPCゲーム画面を見られる人**。
- [D] MVPでは3人が1台のWindows 11 PCを囲み、一人のMinecraft Java Editionキャラクターを操作する。
- [D] 参加者のスマホはゲーム映像の閲覧ではなく、**専用のコントローラー兼ホスト管理リモコン**に使う。
- [M] 遊び終わったら役割を交換して再挑戦したり、別のゲームを選んだりする。**役割交換はMVPのP0ではない**。

### 1.3 プロダクトの独自性の仮説

- [D/M] 改造できない既存ゲームにも（対応する入力条件下で）協力操作体験を後付けする。
- [M] 人数とゲームの特性に合わせた分担を目指す。操作量や役割の重要性が偏らない設計を重視する。
- [E] Minecraftの最初の3分担は、3.2の固定プリセット。自動最適化・任意の役割交換は将来機能。
- [P] **対応可能な「任意のゲーム」は保証しない**。入力API、アンチチート、権限、ゲーム設定によって動作しないタイトルがある。

## 3. 参加者・ホスト・役割

### 3.1 ユーザー識別と割当

- **ROLE-01 [E] P0**：空き枠に**最初に接続したスマホ**をホスト兼**P1（移動）**、次を**P2（視点）**、次を**P3（アクション）**とする。
- **ROLE-02 [D] P0**：ホスト自身も協力プレイの1人としてスマホから操作する。
- **ROLE-03 [E] P0**：Startには、P1の接続と**必要人数（初期値3）**の接続が必要。必要人数はPCのダッシュボードからのみ1〜3に変更できる（試験用）。**4台目は満員として拒否する**。
- **ROLE-04 [E] P0**：切断や再接続で、役割番号やホスト権限を振り直さない。ホストの自動交代はしない。枠を解放するのは、PCのダッシュボードの「リセット」だけ。
- **ROLE-05 [E/P] P0**：
  - [E] 端末で生成した `clientId` をlocalStorageに保存し、再接続時に元の枠へ戻す。同じ端末の別タブは、古いほうを置き換える（終了コード4000）。
  - [P] **未実装の課題**：推測困難なサーバー発行トークンへの強化と、ホストの再認証（NFR-09）。
- **ROLE-06 [D/M] P1**：ホストによる役割の指定・交換（開始前、Pause中）。
- **ROLE-07 [D/M] P2**：2〜4人の可変人数、自動役割分担、プリセットの保存・交換。

## 4. ホスト専用PCリモコン

- **HOST-01 [E] P0**：ホストのスマホは、**PC画面を見ながらPCアプリやゲームのメニューを操作するリモコン**になる。
- **HOST-02 [E] P0**：リモコンの入力は**方向キー4方向、Enter、Esc**。ロビーと一時停止中だけ有効。
- **HOST-03 [D] P1**：仮想タッチパッド・左右クリック等を追加し、メニューやインベントリの操作範囲を広げる。
- **HOST-04 [E] P0**：ゲーム開始前と一時停止中は、**同じリモコン画面**を使う。
- **HOST-05 [E] P0**：ホストのスマホから**START・PAUSE・RESUME・END（ロビーに戻る）**を実行できる。P1以外の命令はサーバーが拒否する。
- **HOST-06 [E] P0**：STARTの後は、ホストのリモコン入力が無効になり、ホストはP1の移動担当になる。PAUSEするとリモコンへ戻る。
- **HOST-07 [D] P0**：PCのゲーム選択やMinecraftのメニューには、キーボードだけで操作できる画面と、マウスが必須の画面が混在する。
- **HOST-08 [H] P0**：MVPでは、ゲームの選択や起動をPC本体のキーボード・マウスで補助してよい。
- **HOST-09 [H] P0**：インベントリの完全な操作はP0では保証しない。デモではホットバーを事前に準備する（P3はEでインベントリを開閉できる）。
- **HOST-10 [P]**：リモコンの送信先（PCアプリかゲームか）を表示・管理する。**未実装**。

## 5. 画面・体験フロー

1. **PC準備 [E]**：PCホストを起動し、ホットスポットをONにする（手動）。ダッシュボードに参加URL・QRと、必要ならWi-Fi接続用QRを表示する。Minecraftは手動で起動する。
2. **スマホのWi-Fi接続 [E]**：スマホ3台をPCのホットスポットに参加させる。「インターネットなし」と表示されても接続を維持する（Androidはモバイルデータを切ると確実）。
3. **Web参加 [E]**：QRを読み、ブラウザでコントローラーを開く。参加順にP1（ホスト）、P2、P3。画面下に経路（`WebRTC+WS`）と往復遅延を表示する。
4. **ロビー [E]**：自分の役割、参加状況、開始の可否を表示する。ホスト以外は待機画面になる。
5. **ゲーム準備 [E]**：ホストがリモコンでゲームのメニューを操作する。
6. **START [E]**：開始条件（3.1）を満たしたときだけ有効。押下中の入力を全解放してから、役割ごとの操作画面へ切り替える。
7. **共同プレイ [E]**：P1が移動・ジャンプ・スニーク・ダッシュ、P2が視点、P3が攻撃・設置・持ち物を担当する。
8. **PAUSE [E]**：ホストのPAUSEで協力入力を止め、全キーを解放してリモコンへ戻る。**Minecraftの時間停止ではない**（Escの自動送信もしない）。
9. **メニュー・管理 [E]**：ホストが必要に応じてリモコンでEsc等を操作する。
10. **RESUME [E]**：ホストが明示的に再開する。開始条件が必要。古い押下は引き継がず、**新しい押下から始める**。
11. **切断 [E]**：誰かが切れたら協力入力を**自動停止**し、その人の押下を解放する。元の枠は保持する。**15秒以内に全員が戻り、WebRTCの接続待ちが終われば自動で協力プレイへ戻る**。期限を過ぎた場合や自動復帰がOFFの場合は、ホストがRESUMEする。
12. **ゲーム変更 [E/H]**：ENDでロビーに戻っても、セッション・接続・役割は維持する。

## 6. 状態機械と入力権限

### 6.1 状態 [E]

| 状態 | 概要 | 許可する入力 | 遷移 |
|---|---|---|---|
| `lobby` | 参加待ち、ゲームの準備 | ホストのリモコンのみ | `START`（開始条件）で `coop` |
| `coop` | 共同プレイ | P1・P2・P3の担当入力、ホストの `PAUSE` | `PAUSE` で `paused`（`host pause`）、切断で `paused`（`Px disconnected`） |
| `paused` | 停止中。`reason` で理由を区別する | ホストのリモコンのみ | `RESUME`（開始条件）で `coop`、`END` で `lobby`。切断が理由の場合は自動復帰あり |

v0.2の状態との対応は次のとおり。

| v0.2の状態 | v0.3の状態 |
|---|---|
| `WAITING_HOST`、`HOST_REMOTE` | `lobby` |
| `COOP_PLAY` | `coop` |
| `PAUSED_REMOTE` | `paused`（`host pause`） |
| `WAITING_RECONNECT`、`HOST_LOST` | `paused`（`Px disconnected`） |
| `SESSION_CLOSED` | ホストの終了（Rust版はCtrl+Cで全解放してから終了） |

### 6.2 規則

- **SM-01 [E]**：PAUSEでMinecraftへEscを自動送信しない。
- **SM-02 [E]**：START・PAUSE・RESUME・END・切断・注入モードの変更・リセットで、キーとマウスボタンを解放し、過去の押下状態を引き継がない。
- **SM-03 [E]**：ホストが切断しても、自動でホストを交代しない。役割の順番を変えない。
- **SM-04 [E]（v0.2から変更）**：切断が理由の停止は、15秒以内（`autoResumeMs`）に全員が戻れば自動で再開する。初期値はON。ダッシュボードでOFFにできる。ホストのPAUSEは自動で再開しない。
- **SM-05 [P] 未実装**：状態変更ごとに `epoch` を更新し、旧状態の遅れて届いた入力をメッセージ単位で拒否する。現在は、状態変更時の全解放、状態ごとの受付制限、接続ごとの入力番号（`nextIseq`）で代替している。
- **SM-06 [E]**：ブラウザを閉じたりスリープしたりしても、サーバーの4秒の監視とスマホの3秒の監視があるので、合成キーを押し続けない。

| 視点 | 不可 | 不可 | **可** | 不可 | 不可 |
| 攻撃・使う・持ち物・E・Q | 不可 | 不可 | 不可 | **可** | 不可 |
| START・RESUME | ホストのみ（条件付き） | — | 不可 | 不可 | ホストのみ（条件付き） |

## 10. 情報・通信・状態の論理仕様

### 10.1 オブジェクト [E]

- **Slot**（P1/P2/P3）
  - 識別と接続：`clientId`、接続、`connected`、`reconnects`、`lastSeen`
  - 入力：`pressed`、`nextIseq`、入力の一時保管（`ibuf`）
  - WebRTC：`rtcState`（`none`/`connecting`/`open`/`failed`）
  - 統計：`via`（先着した経路の件数）、視点の累積値、欠落の統計
  - 切断しても削除しない。
- **Game**：`phase`、`reason`、`required`、`autoResume`、`autoResumeMs`、`autoResumeUntil`。
- **OutputState**（出力ごと）：`holders`（押している枠の集合）、`physical`（実際の押下状態）、`changedAt`、キュー。
- **Look**：未処理分、端数、時定数、到着の途切れの履歴。
- **未実装 [P]**：`sessionId`、`epoch`、`TargetWindow`、`GameProfile`（ゲームごとの対応表）。

### 10.2 主要メッセージ [E]

詳細は [`docs/architecture/protocol.md`](../architecture/protocol.md) を参照する。

```json
{ "type": "hello", "clientId": "…", "ua": "…", "nextIseq": 1 }
{ "type": "welcome", "slot": "P2", "role": "視点", "isHost": false, "reconnected": false }
{ "type": "input", "iseq": 103, "button": "JUMP", "state": "down", "t": 12345.6 }
{ "type": "look", "lseq": 88, "cx": 412.5, "cy": -37.2 }
{ "type": "command", "cmd": "PAUSE" }
{ "type": "game", "game": { "phase": "paused", "reason": "host pause", "connected": ["P1","P2","P3"], "canStart": true } }
```

- クライアントは**操作名だけ**を送る。Windowsのキーコードは送らない。
- `input` はWebSocketとWebRTCの両方に同じ `iseq` で送る。サーバーは番号順に1回だけ処理する。
- `look` はP2専用で、累積値を送る。

## 11. ゲーム選択・登録・起動の位置づけ

1. **P0 [D]**：インストール済みのMinecraftを**ユーザーが自分で起動できれば可**。
2. **P1 [D/M]**：PCアプリの画面で、手動登録したゲームを選ぶ。
3. **P1 [M]**：Steam以外のアプリ・自作ゲームを登録する。
4. **P2 [D/M]**：ランチャーのメタデータからゲームの候補を自動で見つける。
5. **[P]**：ゲームを検出できても、外部入力が通るとは限らない。「発見」と「対応の判定」を分ける。
6. **[P]**：ゲームの選択中・フォーカスの切り替え中は合成入力を全解放する。`on` モードにする前に、前面がゲームであることを確認する（未実装）。

## 14. システム分割

`docs/architecture/system-design.md` を参照する。

- PCホスト（Rust）：受付（HTTP・WS・WebRTC）→ hubスレッド（状態・認可・順序・出力キュー・補間）→ SendInput。
- 画面：ビルド不要の静的HTML（スマホ・ダッシュボード・疑似ゲーム画面）。
- 参照実装：Node.js試作品。同じメッセージ形式・同じ画面を使う。シミュレーションで両者を比較する。

## 15. 開発・検証の順序

1. **G1**：Minecraft Javaで、試作品の `on` モードを使って、キー・クリック・ホイール・相対視点を確認する。
2. **G4-C**：Rust版ホストをシミュレーションと実機3台で、参照実装と比べる。
3. **リポジトリへの取り込み**：Rust版ホスト、画面、参照実装、シミュレーション。あわせてCIを更新する。
4. **未実装の安全要件**：前面ウィンドウの確認（FR-034）、緊急停止キー（FR-035）、トークン（NFR-09）、ログのプライバシー（NFR-13）。
5. **G2-A**：上流回線なしでのホットスポット。
6. **PCアプリの画面**：ゲーム選択・分担の確認（Tauri）。
7. **G5**：3人でのMinecraftのデモの反復、README・発表の準備。

## 16. 未確定事項・チームへの相談事項

- Minecraft Java Editionの**正確なバージョン**、Raw Inputと感度の設定、デモに使うスマホ3台。
- 無線が不安定な端末への対処（端末側の省電力、5GHzへの固定、デモで使う端末の選び方）。
- 切断からの自動復帰（SM-04の変更）を、デモの安全性の観点でチームとして受け入れるか（OFFにもできる）。
- 操作割当の変更（ジャンプ・スニークをP1へ）による操作負荷の偏り（NFR-18）。
