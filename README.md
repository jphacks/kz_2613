# SIGNAL LAB — 電波は、実験して初めて見える。

**一言でいうと**：電波は、実験して初めて見える。

## 製品概要

### 背景（製品開発のきっかけ・課題）

**対象ユーザー**：理科を学ぶ高校生／無線の仕組みを体験したい人。

電波は日常的に使う一方、送信源との距離や配置が通信の観測値にどう影響するかを実感しにくい。

この課題がどの程度頻繁に起きるのか、既存のやり方で解決できていないのかは未検証。まずは実際の利用場面を確認する。

### 製品説明（具体的な製品の説明）

**SIGNAL LAB** は、この場面で必要な行為だけを一つの体験につなげるプロダクトの構想である。

身近なBLEビーコンを置く→スマホを持って測定位置を巡る→強度マップを描く→遮蔽物や距離を変え、予測と結果を比較する。

利用前は「電波は日常的に使う一方、送信源との距離や配置が通信の観測値にどう影響するかを実感しにくい」という状態を想定する。利用後は、電波は、実験して初めて見えるという体験を通じて行動が変わることを目指す。ただし、その変化は今後のユーザー検証で確かめる。

### 特長

1. **利用場面から始める**：理科を学ぶ高校生／無線の仕組みを体験したい人の具体的な一場面に対象を限定し、何でもできる総合アプリにはしない。
2. **最小の実動体験を先に証明する**：BLEビーコン1個を既知の送信源にする／AndroidでRSSIを取得／測定位置はフロア図上に手動ピン留め／観測点だけでグラフ化／条件を変えて2回測る。
3. **既存手段との差を検証する**：ただの「電波AR」より、仮説→介入→実測の体験を主役にする。推定された電波の形を実測と混同しない。

### 解決できること（仮説）

- 対象ユーザーが抱える「電波は日常的に使う一方、送信源との距離や配置が通信の観測値にどう影響するかを実感しにくい」を改善できる可能性がある。
- 使用前/使用後の違いを、説明だけでなく操作・結果の変化として確認できるようにする。
- 運用や導入の手間そのものが増えないかも評価する。

| 1. 開始 | 体験開始・対象や素材の選択 | 入力・権限・前提条件の確認 |

## システム構成（実装案）

```text
ユーザー入力 / センサー・素材
            |
            v
      端末側 UI と検証
            |
            v
      SIGNAL LAB のコア処理
            |
            v
      結果表示 / 音 / 体験
```

- **想定技術**：Android BLEスキャン・ローカルSQLite/JSON・WebまたはAndroidネイティブのマップUI。
- **責任境界**：端末/OSに依存する機能、通信が要る機能、あらかじめ準備するデータを別々に検証する。
- **データの扱い**：同意と権限が必要な情報は収集範囲を限定し、権限不足・通信失敗時にも誤解を与えない。

## 90秒発表のデモ構成（台本案）

- **0–15秒｜背景**：誰がどんな場面で困る/何を面白くしたいのか、一例だけ提示。
- **15–65秒｜ライブ実演**：障害物を置く前後で同じ位置を測り、表示が変わる／実測点と未測定領域を別の表示にする。
- **65–80秒｜Before / After**：体験前と体験後の違いを実際の出力で示す。
- **80–90秒｜意義と制約**：どの条件下で動き、まだ何はできないのかを一言添える。

## 注力したいこと（実装上のこだわり）

- **中心価値**：ただの「電波AR」より、仮説→介入→実測の体験を主役にする。推定された電波の形を実測と混同しない。
- **失敗しても成立する設計**：入力不正・権限拒否・通信断などをハンドリングし、成立しない機能はデモ時に無理に使わない。
- **測定と表現の峻別**：実測、推定、生成演出、手動入力を混同せずに表示する。

## 課題・反証条件
