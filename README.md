# Drift Letter — 手紙は、人の手を渡るほど物語になる。

> この文書は構想の提案であり、動作・性能・導入実績・チーム合意を示すものではありません。製品名・技術構成は仮称/暫定です。

**一言でいうと**：手紙は、人の手を渡るほど物語になる。

## 製品概要

### 背景（製品開発のきっかけ・課題）

**対象ユーザー**：イベントや友人グループで小さなメッセージをつなぎたい人。

SNSでは離れた人にもすぐ届く一方、直接手渡した経緯や偶然のつながりが残りにくい。

この課題がどの程度頻繁に起きるのか、既存のやり方で解決できていないのかは未検証。まずは実際の利用場面を確認する。

### 製品説明（具体的な製品の説明）

**Drift Letter** は、この場面で必要な行為だけを一つの体験につなげるプロダクトの構想である。

一人がメッセージを作る→目の前の人へQRで手渡す→受取人が一言足して次の人へ→移動した履歴が一つの物語になる。

利用前は「SNSでは離れた人にもすぐ届く一方、直接手渡した経緯や偶然のつながりが残りにくい」という状態を想定する。利用後は、手紙は、人の手を渡るほど物語になるという体験を通じて行動が変わることを目指す。ただし、その変化は今後のユーザー検証で確かめる。

### 特長

1. **利用場面から始める**：イベントや友人グループで小さなメッセージをつなぎたい人の具体的な一場面に対象を限定し、何でもできる総合アプリにはしない。
2. **最小の実動体験を先に証明する**：1通を1人が保持する簡易台帳／明示承認つきQRでの所有者変更／受け渡し履歴と追記の表示。
3. **既存手段との差を検証する**：単なるファイル転送ではなく、対面で「渡す理由」とそれまでの旅路をコンテンツにする。

### 解決できること（仮説）

- 対象ユーザーが抱える「SNSでは離れた人にもすぐ届く一方、直接手渡した経緯や偶然のつながりが残りにくい」を改善できる可能性がある。
- 使用前/使用後の違いを、説明だけでなく操作・結果の変化として確認できるようにする。
- 運用や導入の手間そのものが増えないかも評価する。

## 体験フローと画面

|---|---|---|
| 1. 開始 | 体験開始・対象や素材の選択 | 入力・権限・前提条件の確認 |

## システム構成（実装案）

```text
ユーザー入力 / センサー・素材
            |
            v
      端末側 UI と検証
            |
            v
      Drift Letter のコア処理
            |
            v
      結果表示 / 音 / 体験
```

- **想定技術**：スマホWeb/PWA・短命なQRトークン・クラウドDB・取引ID。NFCはOS互換を確認してから。
- **責任境界**：端末/OSに依存する機能、通信が要る機能、あらかじめ準備するデータを別々に検証する。
- **データの扱い**：同意と権限が必要な情報は収集範囲を限定し、権限不足・通信失敗時にも誤解を与えない。

## 90秒発表のデモ構成（台本案）

- **0–15秒｜背景**：誰がどんな場面で困る/何を面白くしたいのか、一例だけ提示。
- **15–65秒｜ライブ実演**：3人が1通を順に渡し、最後の人が「旅路」と追記を見られる。
- **65–80秒｜Before / After**：体験前と体験後の違いを実際の出力で示す。
- **80–90秒｜意義と制約**：どの条件下で動き、まだ何はできないのかを一言添える。

## 注力したいこと（実装上のこだわり）

- **中心価値**：単なるファイル転送ではなく、対面で「渡す理由」とそれまでの旅路をコンテンツにする。
- **失敗しても成立する設計**：入力不正・権限拒否・通信断などをハンドリングし、成立しない機能はデモ時に無理に使わない。
- **測定と表現の峻別**：実測、推定、生成演出、手動入力を混同せずに表示する。

## 課題・反証条件

- 遠隔での不正受領／参加者数の不足／端末互換／非公開情報の拡散。
